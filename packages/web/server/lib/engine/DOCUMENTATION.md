# Engine

OpenChamber drives coding CLIs as child processes. Each CLI is an engine adapter. The shared code here owns sessions, live streaming, permission prompts and the HTTP routes, so a new CLI only maps its own process and output.

## Files

| File | Owns |
|---|---|
| `registry.js` | The list of adapters. The first adapter is the default engine. |
| `routes.js` | Every engine HTTP route, mounted where the OpenCode proxy used to be, behind the UI auth gate. |
| `model-catalog.js` | The model list each adapter serves: read from its CLI in the background, kept in `engine-models.json` in the engine folder (`data-dir.js`) for the next start, and read again on request. See *Model lists*. |
| `catalog.js` | The OpenCode 2.x model and provider records the model picker reads, whether each engine's CLI is installed and signed in, and the readiness answer that greys out an engine in the picker. See *Catalog*. |
| `permission-tiers.js` | The one ladder every engine's permission modes sit on, and the mode a sub-session takes after its parent. See *Sub-session permission modes*. |
| `agent-permission.js` | What an agent may do to permission modes through OpenChamber's tool. See *Sub-session permission modes*. |
| `session-runtime.js` | One live CLI process per session and its queue of prompts. |
| `turn-translator.js` | Engine events of one prompt to OpenCode 2.x wire events, plus the assistant message to store and, while the turn runs, its current state. |
| `wire-messages.js` | Stored messages to the OpenCode 2.x messages the history routes serve, and paging. See *History*. |
| `data-dir.js` | The engine folder that holds `sessions.json`, `attachments/` and `engine-models.json`. Nothing is copied into a new `engine/` folder: the sessions in `~/.openchamber/data` stay with the default instance, which still reads them. |

| `question-form.js` | An engine's `question.requested` as the OpenCode 2.x form the UI renders, and the form reply as the answers per question. See *Questions*. |

| `tool-server.js` | What every adapter needs to hand its CLI OpenChamber's tool server: the child environment that keeps the server's host away from a proxy. See *Tool server*. |
| `tool-file-diff.js` | The `metadata.files` entries an adapter reports with a file change, in the OpenCode 2.x `FileDiff` shape (`file`, `patch`, `additions`, `deletions`, `status`). See *Tool cards*. |
| `tool-instructions.js` | `buildToolInstructions(toolNames)`: the standing instructions that tell an engine which OpenChamber tools exist, to prefer them over generic computer-use, and to report a failed call as failed. See *Tool server*. |
| `session-title.js` | The title of an untitled session after its first prompt. See *Session titles*. |
| `one-shot.js` | One prompt, one plain-text answer, outside any session, through the engine's CLI in print mode. See *Session titles*. |
| `attachments.js` | Files attached to prompts: chunked uploads, their limits, and the copies a prompt claims for its session. See *Attachments*. |
| `attachment-routes.js` | The upload routes and the route that serves a stored attachment to the chat history. See *Attachments*. |
| `attachment-delivery.js` | Which attachments an engine gets as images and which as path lines, HEIC to JPEG with `sips`. See *Attachments*. |
| `session-summary.js` | The compact session list with live state that another OpenChamber window reads to monitor this server. |
| `login-session.js` | Sign-in from the UI: one background login per engine in a pseudo-terminal, the link and device code read from its output, the pasted code typed back. See *Sign-in*. |
| `cli-platform.js` | Finding, spawning, running and stopping a CLI binary from its known install paths, `where.exe` or the login shell. `resolveCliExecutableAsync` runs those lookups as awaited child processes for detection; the synchronous `resolveCliExecutable` remains for the spawn paths. Used by `claude/` and `codex/`. |
| `cli-installer.js` | Version detection, where the CLI came from, and the install, update, uninstall, reinstall and doctor jobs with streamed logs: npm steps for a CLI published on npm, plus the native steps an engine names. Used by `claude/`, `codex/` and `antigravity/`. See *CLI management*. |
| `claude/` | The Claude Code adapter. |
| `antigravity/` | The Antigravity CLI (`agy`) adapter. |
| `codex/` | The Codex CLI adapter. |
| `test/` | `fake-engine.js` for route tests, `fake-codex.js` and the recorded `codex/*.ndjson` transcripts it plays, and the recorded route answers the UI's client test reads (`history-page.json`, `catalog-responses.json`). |

## Adapter contract

`registry.js` rejects an adapter that misses a required field.

| Field | Meaning |
|---|---|
| `id` | Stored on each session as `engine`. Never rename it: stored sessions point at it. |
| `displayName` | Shown to the user. |
| `providerID` | Provider id in `/api/provider` and on wire messages. The registry rejects two engines with the same one, because picking a model picks its engine. |
| `modelCatalog()` | Answers `{ models, defaultModel }` at once, without waiting for the CLI. `models` is a `{ id, name }` list and `defaultModel` one of its ids. A model pick, a create or a `PATCH` with a model outside the list gets 400; a prompt does too, unless the model is the session's stored one, so a chat whose model left the list keeps running. A model may add `family`, and `efforts` when the reasoning levels it offers differ from the adapter's; see *Catalog*. Every adapter answers the list its CLI reported, else the list stored by the last server, else its fallback list (*Model lists*), so a route reads it once per request and uses that answer throughout. The registry checks the answer it gets at registration. |
| `startModelCatalog()` | Optional. Starts reading the models from the CLI in the background. `index.js` calls it once the routes are set up; a second call reads nothing new. Only Codex has it. |
| `startPermissionModeProbe()` | Optional. Starts checking, in the background, which permission modes the signed-in account has. `index.js` calls it once the routes are set up; a second call checks nothing new. Only Antigravity has it (*Permission modes* under Antigravity). |
| `limit` | Optional. `{ context, output }` in tokens, the sizes the CLI states for its models. A missing size is the catalog's conservative one; see *Catalog*. |
| `efforts`, `defaultEffort` | Optional. Reasoning levels the CLI accepts, for every model that lists none of its own. A model's efforts are its variants in the model picker, and a prompt or model pick with an effort the model does not offer gets 400. A model with an empty list, such as Antigravity's `default`, takes no effort, so any effort passes for it. Picking another model of the same engine without a variant keeps the session's effort when the new model offers it, and otherwise sets `defaultEffort`. |
| `permissionModes`, `defaultPermissionMode` | Values the installed CLI and its account accept; a mode that would run as another one is not listed. The list may change while the server runs, so it is read on every use. A mode not listed gets 400 before a process starts or anything is stored. |
| `permissionModeTiers` | Every permission mode's rung on the ladder `read < ask < edits < auto < full` (`permission-tiers.js`), so modes of different engines compare. The registry refuses an adapter that leaves a listed mode without one; a mode listed only later, such as Antigravity's `auto`, is placed up front. |
| `livePermissionModes` | Optional. The modes a running process takes through its `setPermissionMode(mode)`, at once and mid-turn. Any other mode reaches the CLI when its next process starts. See *Session settings*. |
| `dangerousPermissionModes` | The full-permission modes: they let the CLI run every tool without asking. Every engine has at least one, and the registry refuses an adapter without one. The composer marks them, and the first one is where a full-permission mode moves when a chat changes engine. |
| `installer` | `getStatus(force)` (a promise), `runAction(action, { removeConfig })`, `install()` (the `install` action), `getLogs()`, and `log` and `status` events. `getStatus()` reports `installSource`, `actions`, `commands`, `state`, `action`, `installCommand` (what a user runs in a terminal to install the CLI, which the model picker shows for a CLI that is missing), `canInstall` (`actions.install`), `latestVersion` (the npm registry's version, read in the background at most once an hour; `null` until read, offline, or for a CLI not on npm) and `updateAvailable`, true for an npm or native installation behind `latestVersion`. See *CLI management*. |
| `auth` | `status()`, `loginProcess()`, `logout()`, and optionally `loginCommand` and `logoutCommand`. `loginProcess()` returns `{ command, args, shell?, prompts? }`: the CLI's own sign-in that `login-session.js` runs in a pseudo-terminal, and `prompts`, `[{ match, send }]`, keys typed once when the output matches. `logout()` may return a promise; the route answers once it settles. A sign-out the CLI cannot take from a server throws an error that tells the user what to do; the route answers 501 with its message. `status()` never returns or logs what the CLI printed about credentials. `loginCommand` is what a user runs in a terminal to sign in (`claude auth login`, `codex login --device-auth`, `agy` then `/login`); the model picker shows it for an engine that is signed out. `logoutCommand` is the same for signing out (`claude auth logout`, `codex logout`, `agy` then `/logout`). |
| `createProcess(options)` | Returns an engine process. `options` holds `sessionId`, `cwd`, `model`, `effort`, `permissionMode`, `resume` (true when an earlier turn of the session was answered, so the CLI has a conversation to continue), `engineState` and `toolServer` (`{ name, url, token }` or `undefined`; see *Tool server*). |

An engine process is an `EventEmitter` with `isAlive`, `start()`, `sendUserMessage(text, attachments)` (`attachments` as *Attachments* describes, empty when the prompt has none), `respondPermission(requestId, 'allow' | 'deny')`, `respondQuestion(requestId, answers | null)` and `abort()`, plus `setPermissionMode(mode)` (a promise that rejects when the CLI refuses) when the adapter lists `livePermissionModes`. It emits:

| Event | Payload |
|---|---|
| `reasoning.delta` | `{ text }`. Deltas in a row form one reasoning part; text or a tool call in between starts the next part. |
| `text.delta` | `{ text }`. Deltas in a row form one text part; reasoning or a tool call in between starts the next part. |
| `tool.started` | `{ id, name, input }`, as soon as the CLI starts a call |
| `tool.called` | `{ id, name, input }` once the input is final and the call runs. A CLI that reports a call only whole sends this without `tool.started`. |
| `tool.completed` | `{ id, output, isError, metadata? }`: the result as text, whether the CLI calls it a failure, and the metadata the chat draws from, such as `files` diffs (*Tool cards*). The tool server's `describeResult` wins over `metadata` for its own tools. |
| `prompt.merged` | No payload. The CLI took the next queued prompt into the running turn, and that turn's `turn.completed` answers both. |
| `turn.started` | No payload. Optional. The CLI opened a turn: it took a prompt, or began one of its own without a prompt, such as Claude Code answering a background task that finished after its last `result`. With no turn queued the runtime opens one for it, so its output is shown and stored and its `turn.completed` ends it; with a turn queued it changes nothing. |
| `permission.requested` | `{ requestId, toolName, input, summary }` |
| `question.requested` | `{ requestId, title?, questions: [{ id, header?, question, options: [{ label, description? }], multiple, custom }] }`: the agent waits for the user's answer. `custom` lets the user type an answer of their own. See *Questions*. |
| `turn.completed` | `{ outcome: 'succeeded' \| 'failed', usage, error? }`, with `usage` as `{ input, output, reasoning, cacheRead, cacheWrite, total? }` and `error` as `{ type, message }` on a failed turn. The five counts add up every model call of the turn and must not overlap. `total` is the context the turn ended with: what its last model call read and wrote. The context meter reads `total`; without it the UI adds up the five counts, and that sum grows with every tool call, because each call re-reads the whole conversation. An adapter that cannot tell leaves `total` out. |
| `engine.state` | A JSON object the CLI needs to resume this session later, such as its own conversation id. The runtime stores it as the session's `engineState` and passes it to the next `createProcess`. |
| `error`, `exit` | The process failed or ended. |

## Invariants

- Every event on the stream carries an `id` (`stream-hub.js` adds one). The UI drops a wire event without it, which once hid every engine event from the session list, the live status and the unread and failed marks.
- `session.created` names the session's engine (`agent`) and `model`; deleting a session sends `session.deleted`. Other clients learn about new and removed sessions from these.
- A session created without a title has no `title`, in the store, in the session record and in `session.created`. OpenCode's `title` is optional, and each client shows its own word for an untitled session in the user's language. Sessions created before 2026-10-17 got `Yeni Sohbet` as a default title. They keep it, because nothing in the record tells that default from a title the user typed.
- A title change, by `PATCH` or by automatic titling, sends `session.renamed` (`{ sessionID, title }`), which every client applies as a session update.
- The model picker lists every engine's models. Picking another engine's model (`POST /api/session/:id/model`) moves the chat to that engine, with that engine's default effort; while a turn is running it answers 409 and the chat stays put. A CLI cannot resume another CLI's transcript, so a chat with history is marked `handoff`: the next process starts a new conversation (`resume` false, `handoff` true; Claude under a new transcript id it keeps as `engineState.transcriptId`), and its first prompt carries the stored conversation as text (`handoff.js`, newest messages first within 60,000 characters, reasoning left out, tool calls by name). The mark clears when the new CLI reports its `engine.state`. `PATCH` ignores `engine` and `handoff`.
- The permission mode moves with the chat (`carryPermissionMode` in `catalog.js`): it stays when the new engine has it, any other mode becomes the new engine's mode on the same tier, else the nearest one below (`inheritPermissionMode`'s rule), so full permission stays full; a mode without a tier becomes the new engine's default. The controls list each mode's `tier`. A sub-session moves by tier instead (*Sub-session permission modes*). A mode the new engine does not have is never stored. A new-session draft carries its pick the same way when the user picks another engine's model (`carriedPermissionMode` in `useEngineControlsStore`).
- A session starts on the engine it names, else on the engine of the model it is created with (`model.providerID`), else on the default engine, with the model's `variant` as its effort. The composer creates a draft's session this way, so its first send switches nothing.
- The session's wire `model` carries its effort as `variant` when that effort is not the model's default, as an OpenCode record does, so the composer shows the effort the session runs on.
- A stored session without `engine` belongs to the default engine. Those are sessions from before engines existed.
- Only the runtime writes `engineState`. `PATCH` ignores it, so a client cannot point a session at another CLI conversation. It survives a server restart because it is stored with the session. An adapter validates it before use and starts a new conversation when it is missing or invalid.
- A session whose engine is no longer registered stays on disk. Listing skips it and opening it returns 409.
- Each prompt gets its own assistant message. A CLI answers prompts in order, so events go to the oldest unfinished turn. A prompt the CLI took into the running turn (`prompt.merged`) gets none: its turn is dropped from the queue, because waiting for a `turn.completed` that never comes would keep the session busy and give every later answer to the wrong prompt. A turn the CLI begins on its own (`turn.started` with an empty queue) gets an assistant message of its own with no user message before it, and `session.execution.started` goes out for it; without it, the CLI's events had no turn to go to and were dropped, so the chat sat idle while the agent worked on.
- Turn completion advances the live queue and execution status before awaiting storage, so a new background turn that starts during a write begins exactly once.
- An assistant message shows text, reasoning and tool calls in the order the CLI produced them, live and after a reload. Each run of text deltas is its own text part: `session.text.started`, `session.text.delta` and `session.text.ended` with the run's `ordinal`, counted from 0 per message. A run ends when reasoning or a tool call comes next, or when the turn ends. Reasoning runs work the same way with `session.reasoning.*` and their own count. An empty delta starts nothing.
- A tool call becomes `session.tool.input.started`, `session.tool.called` and `session.tool.success` or `session.tool.failed` on the wire, and a tool part in the stored message. A call that ran (`tool.called`) and is still open when its turn ends fails with "The turn ended before this tool finished", so no client shows it running, or a page waiting, forever. A call that was only started is left as it was and not stored, because an adapter may report nothing more about a call and failing it would mark work that succeeded.

**Tool cards.** The chat draws a card from a tool part's name, input and metadata (`packages/ui/src/lib/opencode/tools.ts`), and knows the OpenCode 2.x names. So Codex and Antigravity report their CLI's own tools under those names, with the input each card reads, and report every call through `tool.called` and `tool.completed`:

| Card | Input | Result |
|---|---|---|
| `shell` | `{ command, cwd?, description? }` | the command's output; Codex prefixes `Exit code <n>` and fails the call when the command exits non-zero |
| `read` | `{ path }` | the tool's text (agy reports a summary such as `2 lines, 11 bytes`) |
| `write` | `{ path, content }` | no diff metadata: the card draws the content itself |
| `edit` | `{ path }`, plus `oldString` and `newString` from agy | `metadata.files` with the diff |
| `patch` | `{ changes: [{ path, kind }] }`: a Codex change to several files, a delete or a move | `metadata.files` with each file's diff |
| `grep` | `{ pattern, path }` | the tool's text |
| `webfetch` | `{ url }` | the tool's text |
| `websearch` | `{ query }` | the tool's text |

A tool without a card keeps the CLI's name and input, and the chat shows its input and result as text. Claude Code's tools keep their own names: the chat reads `Read`, `Write`, `Edit`, `Grep`, `Glob`, `WebFetch` and `WebSearch` as the cards above, and draws `Bash` as a generic card with its input and output.

Claude Code's `Task` and `Agent` calls are reported as `subagent` with `{ description, agent, prompt }`, and `TodoWrite` as `todo` with its `{ todos: [{ content, status, activeForm }] }` (`claude/tool-cards.js`). A subagent runs inside the parent's process, so its own calls are not stored; each one it makes is sent as `session.tool.progress` on the `subagent` call with `metadata.activity` (such as `Read src/app.ts`), and the call's completion resets the metadata. The chat appends the activity to the subagent row while it runs and draws only the last `todo` call of a message, as one checklist.
- When the process exits or fails mid-turn, every queued turn ends as `failed` and its partial text is still stored. Abort ends them as `interrupted`.
- Live status uses OpenCode 2.x execution events only: `session.execution.started` when a prompt is accepted or the CLI begins a turn of its own, then exactly one of `session.execution.succeeded`, `session.execution.failed` (with `error: { type, message }`) or `session.execution.interrupted` (`reason: 'user'`) once the session's queue drains. The UI marks a session running and failed from these, and the host's `/api/sessions/status` map reads them from the same stream. Every path that ends a turn sends one, a process that never started included. `/api/session/active` lists the sessions with an open turn; a CLI process stays alive between turns, so a live process alone is not a running session. The engine never sends `session.idle`: OpenCode's `session.idle` carries no outcome, so a failure sent that way read as a success.
- Claude Code reports an API failure as a `success` result with `is_error` set; the adapter treats it as a failed turn and passes the CLI's result text as the error message.
- Permission replies from the UI arrive as OpenCode's `once`, `always` or `reject`. `once` allows the call and `reject` denies it. `always` allows the call, every other request the session is waiting on, and every later request of the session until the session is deleted or the server restarts; stopping the turn, a process exit and a model, effort or mode change keep it; each request it answers gets its own `permission.replied`. Requests carry `save: ['*']` so the UI offers `always`.
- A permission `requestId` is unique across every session, because the control bridge keys pending prompts by it alone. An engine whose CLI numbers its own requests per process maps them to a UUID.
- A question `requestId` is unique across every session for the same reason; it is also the form id.

## Questions

When an agent asks the user something (Claude's `AskUserQuestion`, Codex's `request_user_input`, Antigravity's `ask_question`), the engine process emits `question.requested` and the agent waits. The runtime turns it into a form (`question-form.js`): one field per question, keyed by its `id`, titled by its `header` with the question as the description, or by the question alone. A question with options is a choice list (`multiselect` when `multiple`), with `custom` letting the user type an answer of their own; one without options is a text field. Every field is required. The form's `title` is the engine's, or empty so the UI shows its own "Input needed".

The runtime broadcasts `form.created` with `{ form }`, which the UI shows as the question dock or card and the notification runtime announces like any form ("Input needed", the first question as the body; `../notifications/runtime.js`). The control bridge holds the question with no timeout, unlike a permission, and the session's summary row reads `waiting-input` while it waits. The permission mode and "always allow" do not answer questions.

| Route | Answer |
|---|---|
| `GET /api/form` | `{ location, data }` with the pending forms of the directory's sessions |
| `POST /api/session/:id/form/:formID/reply` with `{ answer }` | 204. `answer` maps each field key to a string, a number, a boolean or a list of strings, else 400 `InvalidRequestError`. The runtime broadcasts `form.replied` and calls `respondQuestion(requestId, { [id]: [answers] })`. |
| `DELETE /api/session/:id/form/:formID` | 204. The user dismissed the question, or sent a chat message while it was open (the UI dismisses open forms then). The runtime broadcasts `form.cancelled` and calls `respondQuestion(requestId, null)`. |

A form the session does not hold answers 404 `FormNotFoundError`, which the UI reads to drop a stale form. A process that exits or is stopped while a question waits ends it as dismissed: `form.cancelled` goes out, and nothing is sent to the stopped CLI.

How each CLI asks and takes the answer:

| CLI | Asks with | Answer | Dismissed |
|---|---|---|---|
| Claude Code | `can_use_tool` control request for `AskUserQuestion`, in every permission mode, `bypassPermissions` included | `allow` with `updatedInput` = the call's input plus `answers: { [question]: "label, label" }` | `deny` with "The user dismissed the question without answering." |
| Codex | server request `item/tool/requestUserInput`; the thread config turns on `features.default_mode_request_user_input`, without which codex-cli 0.163.0 offers the tool only in plan collaboration mode, which OpenChamber does not use | `{ answers: { [questionId]: { answers: [label] } } }` | `{ answers: {} }` |
| Antigravity | a `PreToolUse` hook on `ask_question` (*Questions* under Antigravity) | the hook denies the call with the answers as its reason | the hook denies the call with a reason that says the user closed it |
- `GET /api/config` answers a bare list of config entries, as OpenCode 2.x does: one document whose `model` is the default engine's `provider/model`. The client folds that list for every directory it bootstraps, so a `data` envelope there failed the bootstrap of every directory, Chats included ("Could not initialize workspace").
- In enterprise mode both sign-in routes answer 403 with `code: 'enterprise_mode'` for every engine, before the adapter runs: signing in to a model provider through this server is what the mode closes. Signing out still works. `GET /api/engines/readiness` then gives a signed-out engine no `fixCommand`, so the model picker shows no sign-in command either (*Catalog*). Both read the policy at each request.
- A prompt's user message keeps the `id` the client sent with it, so the UI's optimistic copy of the prompt is the stored message. An `id` that is not `msg_` followed by letters and digits answers 400 `InvalidRequestError`, and one the session already has answers 409 `ConflictError`. Without one the runtime mints an id. The runtime mints ids in OpenCode's ascending format, as the UI does, because the chat breaks a tie in creation time by id.

## Attachments

A prompt (`POST /api/session/:id/prompt` and `/message`) may carry `files: [{ uri, name? }]`, at most 20, and may then have no text. Each `uri` is one of:

| `uri` | What the server does |
|---|---|
| `openchamber-attachment:<id>` | An upload (below). Its file is hard-linked into `sessions/<sessionId>/<id>/`, so one upload can go to several sessions (a parallel run, the server queue). |
| `data:<mime>;base64,…` | Decoded and written into the session folder under the same limits. |
| `file://<path>` | A file on the host the user named; passed by its path, never copied or converted. |

Anything else, an unfinished or unknown upload, or a file over its limit answers 400 (413 for size) `InvalidRequestError` with `field: 'files'` before the user message is stored or a process starts.

**Uploads** (`attachment-routes.js`), behind the UI auth gate like every engine route. `POST /api/attachments` `{ name, mime, size }` answers 201 `{ id, uri }`, or 413 when `size` is over the limit of its kind: images 20 MB, videos 500 MB, other files 50 MB, changed with `OPENCHAMBER_ATTACHMENT_MAX_IMAGE_MB`, `_VIDEO_MB` and `_FILE_MB`. `PUT /api/attachments/:id?offset=N` with an `application/octet-stream` body appends one chunk of at most 8 MB and answers `{ received, complete }`; a chunk that does not start at the bytes received so far answers 409, one past the declared size 413, an unknown id 404, and nothing of a refused chunk is kept. `DELETE /api/attachments/:id` drops an upload. The UI sends 2 MB chunks through `runtimeFetch`, so progress shows and the relay carries them. `GET /api/session/:id/attachment/:attachmentId` serves a claimed file with its type, for the chat history. The chat loads it with `img`, which sends no header and, from another origin, no `SameSite=Strict` cookie, so the route also takes the URL token (`ui-auth.js`); `MessageFilesDisplay` holds a fresh one while the message shows (`useMessageFileUrlToken`).

**Storage** (`attachments.js`). Everything lives under `attachments/` beside `sessions.json`: an upload in `uploads/<uuid>/` (`meta.json` and `data`), a claimed file in `sessions/<sessionId>/<uuid>/<name>`. The server picks every path: ids must be UUIDs, session ids `[A-Za-z0-9_-]`, and the stored name is the base name reduced to `[A-Za-z0-9._-]`, so no request names a path outside the folder. Uploads nobody claimed for a day go at the next upload; a session's folder goes when the session is deleted. File contents are never logged.

**Delivery** (`attachment-delivery.js`, called by the runtime). PNG, JPEG, GIF and WebP are images. A stored HEIC photo is converted to JPEG beside it with macOS `sips` and is an image then; without `sips`, or when it fails, it stays a file. Everything else (video, PDF, text, HEIC that could not be converted) is a file. A file reaches the CLI as a line under the prompt text, `Attachment: <absolute path> (<type>, <size>)`, so the agent opens it with its own tools.

| CLI | Image | Checked against |
|---|---|---|
| Claude Code | an `image` content block, base64 from the file, before the text block; an image over 3.75 MB (5 MB once encoded, the Messages API limit) goes as a path line, which Claude's Read tool scales down | stream-json user message shape |
| Codex | a `{ type: 'localImage', path }` item of `turn/start`'s `input`, after the text item | `UserInput` in the codex-cli 0.163.0 app-server schema |
| Antigravity | a path line; agy 1.4.2's stream input refuses every content block type but text | the agy 1.4.2 binary's own error text |

## Session titles

After every prompt the routes hand the session to `session-title.js`. A session that has a title is left alone, so a title the user typed or a scheduled task set is never replaced, and the store's `title` is re-read before writing, so a rename made while the title was being written wins. Otherwise the first user message of the session is titled once: `one-shot.js` asks the session's engine on its small model (`haiku`, a `luna` or `mini` Codex model, a `flash` agy model, else the engine's default model) for a two to five word title in the language of the message, with the message quoted as source material. When that fails (the CLI is signed out, missing or slow), the title is the first seven words of the message, at most 60 characters. The title is stored, `session.renamed` goes to every client and the session summary is published. The prompt's answer never waits for it; a title arrives within about five to ten seconds.

`one-shot.js` runs the CLI in the temp folder, so no project instructions or hooks load: `claude -p` with no tools, no MCP servers, no setting sources and no saved session; `codex exec --ephemeral` in a read-only sandbox on low effort; `agy -p` with JSON output (agy keeps the conversation in its own history). Claude and Codex read the prompt from stdin. A call that does not answer in 45 seconds is killed.

`POST /api/experimental/generate` (`{ prompt, model?: { providerID, id } }` → `{ data: { text } }`) is OpenCode's one-off generation route, served by the engine of `model.providerID` (else the default engine) through `one-shot.js`. It is what `../small-model` calls, so the manual "Rename with AI", the session goal, commit messages and the walkthrough work on engines. An engine failure answers 503 `ServiceUnavailableError`. Both features need the generator `server/index.js` passes as `generateText`; a server without one (the route tests) titles nothing and answers 503.

## Session settings

A session's model, effort and permission mode are stored on its record. `PATCH /api/session/:id` and `PATCH /api/sessions/:id` check each one against the session's engine before anything is stored: a model the engine does not list, an effort the model does not offer, or a permission mode the engine does not have answers 400 with the `field` it refused (`InvalidRequestError` on the singular route). An effort for a model that offers none is left out. A session that does not exist answers 404. Creating a session checks the same fields. A stored session whose mode its engine no longer offers, such as an Antigravity chat stored in `auto` on an account without it, is moved to the engine's default when it is next read (`GET /api/sessions/:id` and every route that loads one session) or prompted, so it runs instead of being refused. Such a read first waits for the engine's `startPermissionModeProbe()`, so a session read just after a restart keeps a mode the probe is about to list.

The CLI reads its settings when its process starts, and the runtime keeps each process alive between turns. A changed setting reaches the CLI this way:

- **Permission mode, live.** The PATCH hands it to the running process when the adapter lists it in `livePermissionModes` (`applyPermissionMode` in `session-runtime.js`). Claude switches at once, during a turn too, through the stream-json `set_permission_mode` control request an SDK host sends. Claude Code 2.1.302 takes every mode this way except `bypassPermissions`, which it refuses (`bypass_not_launched`) for a process not launched in it.
- **Everything else, at the next prompt.** A prompt whose model, effort or permission mode differs from the live process's replaces that process when it has no open turn: the old one stops without an event, and the new one resumes the conversation (`--resume`, `thread/resume`, `--conversation`). A process still answering a turn keeps its settings until its queue drains, so a prompt it takes into that turn runs on the old ones. A live switch the CLI refused leaves the old mode on the process, so the next prompt replaces it the same way.

`GET /api/engines/controls` tells the composer which modes switch live (*Catalog*).

## Sub-session permission modes

A session with a `parentID` is a sub-session. Its mode is its own: the user changes it with the same PATCH as any session, at any rung, and changing the parent's mode leaves its sub-sessions as they are.

**Tiers.** Each adapter places its modes on one ladder (`permissionModeTiers`): `read` changes nothing, `ask` asks before edits and commands, `edits` edits without asking, `auto` also runs what it judges safe, `full` runs everything.

| Tier | Claude | Codex | Antigravity |
|---|---|---|---|
| `read` | `plan` | `read-only` | `default` |
| `ask` | `manual`, `dontAsk` | `untrusted` | |
| `edits` | `acceptEdits` | | `accept-edits` |
| `auto` | `auto` | `on-request`, `never` | `auto` |
| `full` | `bypassPermissions` | `full-access` | `dangerously-skip-permissions` |

`dontAsk` sits with `manual` because it allows only what the user's settings allow, which `manual` allows too. Codex's `on-request` and `never` run commands inside the workspace sandbox without asking, so they sit on `auto`.

**Inheritance** (`inheritPermissionMode`). A session created with a `parentID` and no `permissionMode` starts in its parent's mode on the same engine. On another engine it takes the most permissive mode at or below the parent's tier, the first one listed when two share it, else the engine's least permissive mode. A parent that does not exist leaves the engine default. A sub-session that moves to another engine (`POST /api/session/:id/model`) is mapped the same way from its own mode, in place of `carryPermissionMode`, so a move never raises its tier: an agent's sub-session is created on the default engine and then moved to the engine of its model, and still lands at the parent's tier.

**Agents** (`agent-permission.js`, through `registerEngineRoutes(...).agentPermissions`, which `index.js` hands to the control service). `setByAgent({ callerSessionId, sessionId, mode })` lets the calling session change a session below it, its sub-sessions and theirs, through the same path as the user's PATCH. It answers 403 for a caller that is not an engine session, for the caller itself, for a session not below it, and for a mode whose tier is above the caller's own; 400 for a mode the session's engine does not have; 404 for a session that does not exist. `checkNewSubSession({ callerSessionId, mode, providerID })` makes the same checks before a sub-session exists, against the engine of `providerID`, or every engine that has the mode when the model is not known yet. The caller is the session the tool grant belongs to (*Tool server*), never one a payload names.

**Claude subagents.** Claude's own Task subagents run inside the parent's process and are no OpenChamber session, so they run in the parent's process mode and nothing here applies to them.

## History

`GET /api/session/:id/message` and `GET /api/session/:id/message/:messageID` serve a chat's history as the OpenCode 2.x records `@opencode/client` returns and the UI projects (`packages/ui/src/lib/opencode/projection.ts`). A reload draws the chat from them, so they must give the same messages and parts the live events drew.

**Records.** A user message is `SessionMessageUser`: `{ id, time: { created }, type: 'user', text, files? }`. `files` lists the prompt's attachments as `PromptFileAttachment` records with an empty `data` and `source: { type: 'uri', uri }`, where `uri` is the stored copy's `/api/session/<id>/attachment/<attachmentId>` or the `file://` URL of a host file the prompt named; the stored message keeps `files: [{ uri, name, mime }]`, and `session.inbox.enqueued` carries the same records. Context the client admitted with `POST /api/session/:id/synthetic` (terminal output, standing session context) is kept on the next user message as `context` and read back as `SessionMessageSynthetic` records `{ id, time: { created }, type: 'synthetic', text, description, metadata }` right before it, each also announced live as a `synthetic` inbox item; the CLI gets their text ahead of the prompt, and `text` stays what the user typed. An assistant message is `SessionMessageAssistant`: `{ id, time: { created, completed }, type: 'assistant', agent, model: { providerID, id }, content, finish, cost, tokens }`. `content` holds `{ type: 'text', text }`, `{ type: 'reasoning', text, time }` and `SessionMessageAssistantTool` items: `{ type: 'tool', id, name, executed, state, time: { created, ran, completed } }`. A tool `state` is `completed` with the result as text `content` and the call's `metadata` (`metadata.openchamber` for pages), `error` with `{ type: 'tool', message }` and the result text when there is one, `running` with `metadata: {}`, or `streaming` for a call only started.

**Ids line up with the live stream.** The UI derives part ids from content position: the n-th text item of a message is `<messageID>:text:<n>`, the n-th reasoning item `<messageID>:reasoning:<n>`, a tool item its call id. The stored message keeps the turn's parts in stream order, one per run of text or reasoning, so the run streamed with ordinal n is the n-th item of its type read back. The translator never stores an empty run, because the history leaves empty text out and that would shift the count of every later item. A call that was only started is left out at the end of the turn, which shifts nothing, since a tool item goes by its call id. The assistant message id is the `assistantMessageID` of the turn's events, the user message id the `inboxID` of `session.inbox.enqueued`, and both carry the same creation time as their event. A record stored before runs were split holds at most one text and one reasoning part, each where its first delta arrived, and still reads that way.

**What is stored.** The translator stores an assistant message with `createdAt` (when `session.step.started` went out), `completedAt`, `outcome` (`succeeded`, `failed` or `interrupted`), `tokens` and its parts. `tokens` is what `session.step.ended` carried: the turn's counts, plus `total` when the adapter reported one. Reasoning parts keep `time: { created, completed }`, tool parts `executed` and `time: { created, ran, completed }`. The outcome reads as `finish`: `stop`, `error` or `unknown`, the same value `session.step.ended` carries. Records stored before these fields existed still read: a missing completion is the creation time, a missing outcome reads as `stop`, a part without times takes the message's, and text kept under `content` (the plural routes) is read from there. A message or part that cannot be read is left out and the rest of the history still loads.

**Running turns.** The store gets a turn's message when the turn ends. Until then the history adds the turn's current state from the runtime (`openMessages`), without `time.completed`, `finish`, `cost` or `tokens`, and with calls still running or only started. A reload during a turn keeps it on screen, including a page that waits for the user's answer, and later events continue it. The message moves to the store in the same tick its turn leaves the runtime, so a read never lists it twice.

**Paging.** The list honours `limit`, `order` and `cursor`, and `type` as a filter. Messages are ordered by creation time, a tie in the stored order. The default is newest first. `cursor.next` continues after the page's last message in the same order and is null once nothing remains; `cursor.previous` is always null, because no client walks back. A cursor names its order, so combining it with `order` answers 400 `InvalidRequestError`, as OpenCode does. A cursor that names no message of the history answers 400 `InvalidCursorError`, and a malformed query 400 `InvalidRequestError`. A missing message on the single-message route answers 404 `MessageNotFoundError`.

**Contract test.** `history.test.js` records a page in `test/history-page.json` (rewrite it with `vitest -u` after a deliberate change). `packages/ui/src/lib/opencode/client.test.ts` feeds that file through the real client and projection and checks the parts the live stream would have drawn.

## Catalog

The composer's model picker, its reasoning picker and the MCP lists read OpenCode 2.x routes through `@opencode/client` (`getProvidersForConfig`, `listMcpServers` in `packages/ui/src/lib/opencode/client.ts`). `catalog.js` builds the records from the adapters, so the adapter's `modelCatalog()` is the only source. Every answer carries `location: { directory }`, the directory of the `x-opencode-directory` header. No engine's catalog depends on the directory.

| Route | Answer |
|---|---|
| `GET /api/model` | `{ location, data: ModelInfo[] }`, every model of every engine in registry order |
| `GET /api/model/default` | `{ location, data: ModelInfo }`, the default engine's `defaultModel`, the model `/api/config` names |
| `GET /api/provider` | `{ location, data: ProviderInfo[] }`, one provider per engine |
| `GET /api/mcp` | `{ location, data: McpServer[] }`, OpenChamber's tool server when one is wired |

**Models.** A model reads as `{ id, modelID, providerID, family, name, capabilities, variants, time, cost, status, enabled, limit }`.

- `id` and `modelID` are the adapter's model id, `providerID` the adapter's. Picking the model sends that pair to `POST /api/session/:id/model`.
- `variants` are the model's `efforts`, else the adapter's, as `{ id }`. The reasoning picker sends the chosen one as `variant`, which the session model route stores as the effort. Antigravity's `default` model passes no `--effort` and lists none.
- `capabilities` is `{ tools: true, input: ['text', 'image', 'pdf', 'video'], output: ['text'] }` for every model. Every engine gets what the composer attaches: an image natively where its CLI takes one, anything else as a path its tools open (*Attachments*), so the composer warns about no image, PDF or video.
- `limit` is the size a model reported through `adapter.modelLimit(modelId)`, else the adapter's `limit`, with any size it leaves out taken from `{ context: 200_000, output: 32_000 }`. Those are below the sizes of every model the engines list, so the context meter never shows more room than a model has. A 0 stands for unknown: the UI then shows the used tokens without a percentage and prints no size. Each engine's sizes and their source follow the list.
- `cost` is empty. The CLI bills its own account, and a zero price would show the model as free. `time.released` is 0, `status` `active` and `enabled` true.

| Engine | `limit` | Source |
|---|---|---|
| Claude Code | 1M context, 128K output | Claude Code 2.1.301 resolves the aliases to claude-sonnet-5-5, claude-opus-5-5 and claude-haiku-5-5, and its own model table gives each a native 1M window and 128K output tokens. |
| Codex | 272K context, 32K output; the reported window once a turn ran | The model catalog bundled with codex-cli 0.163.0 gives every listed model a 272K context window and no output cap. `model/list` names neither. `thread/tokenUsage/updated` carries `modelContextWindow` (codex-cli 0.162.1 schema); the process emits it as `model.limit` for its model, the adapter keeps it in memory and announces a catalog change, so the model's `limit.context` becomes that window. |
| Antigravity | 0 (unknown) | agy 1.4.2 states no sizes: `agy models` has no detail flag, and neither `/model`, `/help` nor `/usage` in print mode names a window. |

**Providers.** A provider reads as `{ id: providerID, name: displayName, activation, package: 'openchamber/engine/<id>' }`. `activation` is `enabled` when the engine's CLI is installed and signed in and `auto` otherwise, which includes a CLI that is missing and one not checked yet. The UI lists both the same way, so every engine stays in the picker. `disabled` is never sent. In OpenCode it is the user's off switch, and the UI hides such a provider.

**Controls.** `GET /api/engines/controls` answers `{ data: [{ engine, providerID, defaultPermissionMode, permissionModes, defaultEffort }], default }`, one entry per engine in registry order, built from the adapters without running a CLI. Each permission mode is `{ id, labelKey, descriptionKey, dangerous, appliesLive }`: `labelKey` and `descriptionKey` are the UI message keys `engine.permissionMode.<engine>.<mode>.label` and `.description`, which the UI translates; `dangerous` comes from `dangerousPermissionModes` and `appliesLive` from `livePermissionModes`. `defaultEffort` is the adapter's, or null. The composer's Permission and Effort controls read it through `useEngineControlsStore` (`packages/ui/src/stores`); a 404 there means a server without engines.

**Readiness.** `GET /api/engines/readiness` answers `{ data: [{ engine, providerID, state, fixCommand }] }`, one entry per engine in registry order. `state` is `ready`, `not-installed`, `signed-out`, or `unknown` for an engine not checked yet or whose check threw. `fixCommand` is the installer's `installCommand` for `not-installed`, the adapter's `auth.loginCommand` for `signed-out`, and `null` otherwise. In enterprise mode it is `null` for `signed-out` too, because the mode closes signing in to a model provider through OpenChamber; the route reads the policy at each request. The install command stays in enterprise mode: installing a CLI adds no provider, key or endpoint, and the CLI still needs the sign-in the mode refuses. Nothing the CLI reported about the account is in the answer. The composer's model picker greys out the models of a `not-installed` or `signed-out` engine, names the reason on the provider's header and, when there is one, shows `fixCommand` with a copy button; an `unknown` engine stays selectable, so nothing is greyed out before the first check. The UI reads it through `useEngineReadinessStore` (`packages/ui/src/stores`). A prompt to an engine whose CLI cannot run still fails with the error from starting or running it.

Neither route waits for a CLI. `createEngineAvailability` answers the last known state and, when that is missing or stale, checks after the response went out: `installer.getStatus()` first, then `auth.status()` when the CLI is installed. A `ready` state is stale after 30 seconds, any other after 5, so an engine the user just installed or signed in to is offered again the next time the picker opens. One check runs per engine at a time. The first read after a start therefore answers `auto` and `unknown` for every engine. The UI renders `enabled` and `auto` alike, so the server sends no catalog event when a check changes one.

**MCP.** Each CLI loads the MCP servers of its own configuration, and OpenChamber adds only its tool server to each process (*Tool server*). The list names that server, `{ name: 'openchamber', status: { status: 'connected' } }`, while a `toolServer` provider is wired, and is empty otherwise. Antigravity does not load the tool server yet, which the list does not show. Connecting the tool server answers 204 and changes nothing. Connecting or disconnecting any server, `PUT` and `DELETE` on `/api/experimental/mcp/:server`, and disconnecting the tool server answer 400 `InvalidRequestError` with a message that says what to do instead. The status is 400 because the client keeps the body only of a status the route declares, and those routes declare 400, 401 and 404, so a 501 would have reached the UI as "unexpected status".

**Contract test.** `catalog.test.js` checks each answer against strict zod restatements of `ModelListOutput`, `ModelDefaultOutput`, `ProviderListOutput` and `McpListOutput` from the client's generated types, and records the answers in `test/catalog-responses.json` (rewrite it with `vitest -u` after a deliberate change). `packages/ui/src/lib/opencode/client.test.ts` feeds that file through the real client and checks the providers, models, variants and the MCP error the UI gets.

## CLI management

The Engines screen in Settings installs, updates, repairs and removes each CLI through these routes.

**`GET /api/engines`** answers `{ data, default }` with one entry per engine. Besides the version fields, each entry has:

| Field | Meaning |
|---|---|
| `installSource` | `npm` (found through the package's `package.json`), `native` (the CLI's own installer: Claude Code's link in `~/.local/bin` into `~/.local/share/claude`, agy's binary in `~/.local/bin`), `brew` (the binary resolves into a Homebrew `Cellar` or `Caskroom`), or `unknown` (missing, or found anywhere else). |
| `actions` | `{ install, update, uninstall, reinstall, doctor }`, each true when the server can run it for this installation. |
| `commands` | `{ install, update, uninstall, reinstall, doctor, login, logout }`, the command each step runs or a user runs in a terminal, `null` when there is none. `login` and `logout` come from the adapter's `auth`. |
| `state`, `action` | `state` is `idle`, `installing` while any action runs, `completed` or `failed`; `action` names the running or last action, `null` before the first. |
| `autoUpdate` | `{ enabled, lastRun }`: the engine's switch from `engineAutoUpdate` in `settings.json`, and the last automatic update as `{ at, from, to, ok, error }` (`null` until one ran since the server started). |
| `latestVersion`, `updateAvailable` | The npm registry's version, for a native Claude Code too; `null` for agy, which is not on npm. |

What each installation runs:

| Installation | install / update | reinstall | uninstall | doctor |
|---|---|---|---|---|
| Missing CLI | `npm install -g <package>@latest`; agy runs its install script | — | — | — |
| npm | `npm install -g <package>@latest` | `npm install -g <package>@latest --force` | `npm uninstall -g <package>` | `<command> doctor` (Claude Code, Codex) |
| Claude Code native | `claude update` | `claude install latest --force` | removes `~/.local/bin/claude` and `~/.local/share/claude` | `claude doctor` |
| agy native | `agy update` | the install script | removes `~/.local/bin/agy` | none: agy has no doctor |
| Homebrew or unknown | — | — | — | `<command> doctor` |

**Detection.** `getStatus()` never blocks the event loop: finding the binary (`where.exe` or the login shell) and `<cli> --version` run as child processes it awaits, and agy's detection works the same way. Concurrent reads share one detection in flight. A found CLI is kept for 15 seconds and a missing one for 5, so a CLI installed in a terminal shows up within that window; `getStatus(true)`, a `refresh=true` query and the end of every job detect again. `runAction` detects before it starts and rejects with `busy` when another action started meanwhile.

`install` on an installed CLI is its update. npm is resolved from `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and `~/.npm-global/bin` before the bare name; the command shown is `npm ...` either way. `claude doctor` and `codex doctor` print a report and exit without a terminal (checked with stdin closed: Claude Code 2.1.300 in about a second, codex-cli 0.162.1 in about seven), so they run as jobs.

`uninstall` keeps the configuration unless the body sets `removeConfig: true`, which also removes what exists of `~/.claude` and `~/.claude.json` (Claude Code), `~/.codex` (Codex) or `~/.gemini/antigravity-cli` (agy). Native paths come from the home folder and the detected command, never from the request: Claude Code counts as native only when the command is the `~/.local/bin/claude` symlink and its target lies inside `~/.local/share/claude`; agy only when the command is a regular file at `~/.local/bin/agy`. Before the first step, every path to remove is checked to lie inside the home folder, and the job fails without running anything otherwise.

**`POST /api/engines/:engine/actions/:action`**, with `action` one of `install`, `update`, `uninstall`, `reinstall`, `doctor` and an optional body `{ removeConfig }` (read for `uninstall` only), answers 202 `{ status: 'running', action, message }` and runs the job in the background. It answers 400 `{ error, command }` when `actions[action]` is false, with the command for a terminal or `null`; 409 `{ error, action }` while another action of the engine runs (one job per engine); 404 for an unknown action. `POST /api/engines/:engine/install` and `POST /api/engine/install` are the `install` action.

**Auto update** (`auto-update.js`). `PUT /api/engines/:engine/auto-update` with `{ enabled }` stores the switch in the host's `settings.json` (`engineAutoUpdate`, an `{ [engineId]: boolean }` map, off by default) and answers the engine's entry; it answers 501 on a server started without the `autoUpdateSetting` dependency. The server checks every 5 minutes, 30 seconds after start and 20 seconds after a switch is turned on, because the latest version is read in the background. For each engine whose switch is on, whose CLI is installed and behind `latestVersion`, and whose `update` action is available, it runs that action, which is the official command in the table above on macOS, Linux and Windows. It waits while any session of that engine has a turn open (`runtime.hasRunningTurn`) or an installer action runs. A failed update is logged, kept in `autoUpdate.lastRun` and not retried for the same version for 6 hours.

**`GET /api/engines/:engine/install/stream`** streams every action as SSE: a `status` event with the current status first, the logs so far, then `log` events (`{ stream: 'stdout' | 'stderr' | 'system', text, timestamp }`) and `status` events (`{ state, action, result?, error? }`).

**Sign-in.** `POST /api/engines/:engine/auth/login` starts the adapter's `loginProcess()` in a pseudo-terminal (node-pty; bun-pty under Bun), 200 columns wide so a link is not wrapped, in the home directory with the server's environment, and answers the session; while one runs for the engine it answers that one. `GET` answers `{ state, url, code, needsInput, message, outputTail }`: `state` is `idle`, `starting`, `waiting` (a link or code was printed), `succeeded`, `failed` or `cancelled`. `url` is the first `https` link that does not point at this machine, from OSC 8 hyperlinks or the printed text with ANSI codes removed and wrapped lines joined; `code` is a one-time code such as `ABCD-1234` on a line of its own; `needsInput` is true while the output asks to paste something; `outputTail` is the last 4000 characters of plain output. `POST .../auth/login/input` `{ text }` types the text, then Enter 300 ms later, and answers 409 when no sign-in runs. `DELETE .../auth/login` stops it. A sign-in succeeds when `auth.status()`, polled every 2 seconds, turns signed in (only for an engine signed out when the sign-in started) or the CLI exits 0, and fails on another exit or after 10 minutes; the CLI is stopped then, and the readiness and model list are refreshed. Enterprise mode answers 403 and an adapter without `loginProcess()` 501 with its `loginCommand`. The output stays in memory and is never logged.

When a job ends and after every sign-out, the engine's readiness is dropped, so the next readiness read checks the CLI again (`availability.invalidate`). `POST /api/engines/:engine/auth/logout` answers 200 only when the CLI signed out; Claude Code's non-zero `claude auth logout` exit or timeout answers 501 with the step to take, like Codex.

## Model lists

`model-catalog.js` gives every adapter the same catalog: `modelCatalog()` answers at once, `startModelCatalog()` starts the first read, `refreshModelCatalog()` reads now and rejects when that read fails, and `onModelCatalogChange(listener)` is told when the served list changes. Before the server starts it, the catalog reads nothing. After that it reads again in the background after 10 minutes, or when the installer reports another binary or version, at most one read at a time; a failed read keeps what was served. A read whose `defaultModel` is not listed serves its first model as the default. Each list that changed is written to `engine-models.json` in the engine folder, which the next server serves until its own first read lands, and broadcast on the `global` stream as `model.updated` (`data: { engine }`), which makes every UI read `/api/model` and `/api/provider` again.

| Engine | Read | No turn, no quota |
|---|---|---|
| Claude Code | `claude -p --settings '{"disableAllHooks":true}' --input-format stream-json --output-format stream-json --verbose`, one `initialize` control request, the `models` of its `control_response`, then the CLI is stopped (20 s limit). `default` is left out; each other `value` is a model with its `displayName` and `supportedEffortLevels` (none means it takes no effort). `sonnet`, `opus` and `haiku` stay listed when the CLI leaves one out; `sonnet` is the default. Hooks are off for the read, so the user's `SessionStart` hooks do not run. | `initialize` answers before any prompt. |
| Antigravity | `agy models`. `<base>-<effort>` lines group into one model `<base>` whose efforts are the suffixes (`low`, `medium`, `high`, `xhigh`, `max`) and whose name drops the `(Effort)` suffix. `default` comes first and stays the default. An empty list (no account) fails the read. | A listing. |
| Codex | `model/list` of `codex app-server` (*The Codex adapter*). | No thread is started. |

The server reads every list again when a CLI job (`POST /api/engines/:engine/actions/:action`) ends, after a sign-out, and when a readiness check finds an engine's state changed (installed, signed in or out) since its last check. `POST /api/engines/:engine/models/refresh` reads one engine now and answers `{ engine, providerID, models, defaultModel, error }`, 200, or 502 with the list it keeps serving and the read's error; `POST /api/engines/models/refresh` reads every engine and answers `{ data: [...] }` with one such entry each. Settings → Engines offers it as *Refresh models*.

## Session summary

`GET /api/sessions/summary` answers `{ sessions, projects }`, one row per listed session: `{ id, parentID?, title, directory, engine, updatedAt, state, outcome?, chat?, projectId, work }`. `work` is `'open'` while the session's work metadata (`session-work/state.js`) is open, else `null`; the sidebar's In work zone reads it for every watched host. `projects` is this server's project list from its settings (`projects`, `defaultProjectId`), read on every snapshot: `{ id, label, path, order, isDefault }`, where `order` is the saved (manual) position and `label` falls back to the folder name. `projectId` is the id of the deepest project whose folder is the session's folder or holds it (a path match on a `/` boundary), or `null`; a worktree outside its project's folder is not matched, since that would take a git call per row. `chat: true` marks a session of the managed Chats: its folder is inside one of the chats roots the server passes in (`chatRoots`, the default `chats` folder and `OPENCHAMBER_CHATS_DIR`), so a watching window lists it under Chats instead of as a folder of its own. `GET /api/sessions/summary/stream` is SSE: a `{ type: 'snapshot', sessions, projects }` event first, then `{ type: 'session', session }` whenever a session's state, pending request, title or work state changes, `{ type: 'removed', id }` when one is deleted, and a `: heartbeat` comment every 15 seconds. When a settings save changes `projects` or `defaultProjectId`, the settings runtime calls `summary.refreshProjects()` (wired in `server/index.js` through the `onProjectsChanged` hook) and the stream sends a whole new `snapshot`, so every row is regrouped; a new event type would make an older client drop the stream, a snapshot it already applies. Clients that do not know `projects` or `projectId` ignore them. Both are registered before `/api/sessions/:id` and sit behind the UI auth gate like every route here. Neither carries message content. The client is `packages/ui/src/lib/hosts/`.

`state` is read from the owner of each fact when a row is built:

| State | Source |
|---|---|
| `waiting-permission` | The control bridge holds an unanswered request for the session. |
| `running` | The runtime has a prompt queued or being answered (`isTurnActive`). A live process between turns is not running. |
| `failed` | The last finished turn failed and no new one started. |
| `idle` | Anything else. |

`waiting-input` means the control bridge holds an unanswered question (*Questions*); it comes after `waiting-permission`. `outcome` is the last finished turn's `succeeded`, `failed` or `interrupted`, kept in memory only, so after a restart every session reads `idle` without one.

The runtime announces each turn start and end (`subscribeActivity`), the control bridge each change to a session's pending requests (`subscribe`), including the silent timeout, and the routes announce creation, title edits, an engine switch from the model picker and deletion. A notification that leaves the row unchanged sends nothing.

4. If the CLI can call an MCP server over HTTP, give it `options.toolServer` (*Tool server*).
5. Register the factory in `packages/web/server/index.js`, after Claude so Claude stays the default.
6. Add a test with the CLI's recorded output. `test/fake-engine.js` shows the process shape the runtime expects.

## Tool server

OpenChamber's own agent tools (the in-app browser, render page, project knowledge, session control, notify; `../agent-tool/DOCUMENTATION.md`) reach every engine as one MCP server over HTTP. The engine never sees how they are served: `routes.js` takes an optional `toolServer` provider, `{ name, grant, describeResult }`, which `index.js` wires to the agent-tool runtime's `engineToolServer`. `name` is the server's MCP name, `openchamber`, which the MCP list shows (*Catalog*).

**Lifecycle.** When the runtime starts a CLI process it asks `toolServer.grant({ sessionId, directory })` for a grant and passes its `server`, `{ name, url, token }`, to `createProcess` as `options.toolServer`. The token is fresh for each process, and the server binds it to that session and directory on its side, so a call cannot name another session. When the process ends, for any reason, the runtime revokes the grant: the token stops working and its running calls are aborted. A prompt for a live process calls the grant's `noteUserMessage()`, which ends a page waiting for the user's answer so the CLI does not hold the message behind it. A grant that fails, such as before the listener has a port, leaves the session running without the tools and logs why. Without a provider (tests, or a server that does not wire one) `options.toolServer` is `undefined`.

**What an adapter does with `options.toolServer`.**

1. Register an HTTP (Streamable HTTP) MCP server named `name` at `url`, sending `Authorization: Bearer <token>`. Keep the token out of argv, which `ps` shows every user: a private file, the CLI's stdin, or an environment variable the CLI reads, in that order of preference.
2. Spawn with `toolServerEnvironment(url)` from `tool-server.js` as the child's environment. It is the whole environment with the server's host added to `NO_PROXY`, so a proxy never receives the token.
3. Let the tools run without a permission prompt. Their limits are enforced on the OpenChamber side (the settings that switch each tool off, a fixed action allowlist, nothing destructive), and a prompt for every browser click makes them unusable.
4. Report the server's tools by their own names (`openchamber_render`, not the CLI's namespaced form). The chat renders them by those names.
5. Emit `tool.called` and `tool.completed` for them. The runtime asks the provider's `describeResult(name, output)` for the metadata the chat draws a page from.
6. If the CLI can put its own tool call id in the MCP request's `_meta`, add that key to `CALL_ID_META_KEYS` in `../agent-tool/mcp-server.js`. A page can wait for the user's answer only then, because the chat answers by the call id it shows; otherwise the agent is told to ask in text.
7. If the CLI takes a prompt that arrives mid-turn into the running turn, emit `prompt.merged` when it does.

**Instructions.** A CLI does not prefer a tool it was never told about (Codex reached for its computer-use tool to drive the browser panel, and an engine reported `drivable: false` as a dead end). The provider's `instructions()` builds the text from the tools the settings turn on now (`tool-instructions.js`) and is `null` when none is on; the runtime passes it to `createProcess` as `options.toolInstructions` only together with a granted `toolServer`, so a session without the tools carries nothing extra. The text names `openchamber_web` for the browser panel, states that a `drivable: false` page is display-only (the web build; the desktop app drives it) and asks for the working fallback instead of a success claim, and requires a failed call to be reported as failed. The channel is per CLI: Claude Code `--append-system-prompt`, Codex `developerInstructions` in `thread/start` and `thread/resume`, Antigravity a rule file in its tool plugin (below).

**Claude Code.** `claude/mcp-config.js` writes `{"mcpServers":{"openchamber":{"type":"http","url":…,"headers":{"Authorization":"Bearer …"}}}}` into a file of its own: a fresh `mkdtemp` directory (0700) with one file written 0600, removed when the process exits or fails to spawn. `--mcp-config <file>` names it, so the token is neither in argv nor in the environment the agent's shell commands inherit. `--strict-mcp-config` is not passed, so the user's own MCP servers still load. `--allowedTools mcp__openchamber__*` pre-allows the tools: `dontAsk` would otherwise deny them, `auto` would leave each call to its classifier, and `manual` would ask for every browser action; a deny rule in the user's own settings still wins. Claude defers MCP tools behind its tool search unless a tool asks to load up front, which the server does unless Code Mode is on. Claude names the tools `mcp__openchamber__<tool>`; the adapter strips that prefix. Every `tools/call` carries `_meta["claudecode/toolUseId"]`, the id of the tool part in the chat, so pages can wait. Claude takes a prompt that arrives mid-turn into the running turn at its next tool boundary and answers both with one `result`; with `--replay-user-messages` it echoes each prompt when it takes it, and the adapter emits `prompt.merged` for an echo that arrives while a turn is open. Checked against Claude Code 2.1.301.

**Codex.** `thread/start` and `thread/resume` carry `config.mcp_servers.<name>` with the `url`, `bearer_token_env_var: "OPENCHAMBER_MCP_TOKEN"` and `default_tools_approval_mode: "approve"`, and the token is in that variable of the app-server's environment, never on the stdin channel, so Codex does not write it into the thread it stores. The name matches Codex's default shell-environment excludes (`*KEY*`, `*TOKEN*`), which keep it out of the commands Codex runs while `shell_environment_policy.ignore_default_excludes` is off. Checked against codex-cli 0.163.0 without a signed-in account: `thread/start` accepts the config, Codex connects at once, sends the bearer from the variable and lists the tools. Not checked: whether the excludes are on by default, whether `approve` keeps every call from asking, and whether Codex sends its call id in `_meta` (the `tools/list` request carried only a progress token, so its pages probably cannot wait yet). `item/started` of an `mcpToolCall` gives `tool.started` and `tool.called`, since its arguments are already final, and `item/completed` gives `tool.completed`.

**Antigravity.** agy has no MCP flag, and `agy mcp add` writes the user's global `~/.gemini/config/mcp_config.json`. It does load plugins from every workspace root, and `--add-dir` adds one for the run. `antigravity/tool-plugin.js` therefore writes a fresh `mkdtemp` directory (0700) holding `.agents/plugins/openchamber/` with `plugin.json`, the question hook (*Questions* under Antigravity; also without a tool server, except on Windows), `mcp_config.json` (`{"mcpServers":{"openchamber":{"url":…,"headers":{"Authorization":"Bearer …"}}}}`, 0600) and the tool instructions as `rules/AGENTS.md`, which agy injects as a rule. The process passes it as `--add-dir <dir>`, keeps `cwd` as the primary workspace, spawns with `toolServerEnvironment(url)`, and removes the directory when agy exits, fails to spawn or is aborted. Nothing in the user's agy config changes; agy only caches the tool schemas under `~/.gemini/antigravity-cli/mcp/openchamber_openchamber/`. agy namespaces a plugin's server as `<plugin>_<server>`, so calls arrive as `call_mcp_tool` steps with `ServerName: "openchamber_openchamber"`, `ToolName` and `Arguments`; the process reports those by `ToolName` with `tool.started`, `tool.called` and, at the step's `DONE` or `ERROR` update, `tool.completed` with `tool_info.output` (the call's result text) or `tool_info.error.message`. A call to another MCP server is reported as `mcp__<server>__<tool>` the same way.

Step 3 cannot be met per session: every agy permission store (`settings.json`, `~/.gemini/config/projects/*.json`, `config.json`) is global, plugin `PreToolUse` hooks that answer `allow`, with or without `permissionOverrides`, do not lift the headless refusal, and `--mode auto` does not allow MCP calls. So the tools run only in `dangerously-skip-permissions`, or where the user added an allow rule such as `mcp(openchamber_openchamber/*)`; in any other mode a call is refused like a shell command (*Permission modes*). agy sends no call id in `_meta`, so its pages cannot wait for the user's answer. Checked against agy 1.4.0 on macOS, 2026-10-17: the tools list, `openchamber_render` runs and its result and metadata reach the chat, and the rule text is followed.

## The Antigravity adapter

`antigravity/` drives Google's Antigravity CLI. Facts checked 2026-10-16 against agy's changelog up to 1.4.0 and the public captures listed at the end.

**Process.** One long-lived `agy --input-format stream-json --output-format stream-json` per session, available since agy 1.1.15. Each stdin line `{"event":"user","message":{"content":"..."}}` runs one turn of the same conversation. agy prints an `init` event, `step_update` events and one `result` per turn, and keeps running after the `result`. Its docs say to wait for the `result` before writing the next prompt, so `AgyProcess` queues prompts and writes one at a time.

**Resume.** agy picks the conversation id and reports it in `init.conversation_id`. The process emits it as `engine.state` `{ conversationId }` and passes it back as `--conversation <id>` in the next process. When agy cannot find that conversation it starts a new one; the new id replaces the stored one and earlier context is lost to the CLI, while OpenChamber keeps its stored messages.

**Events.**

| agy output | Engine event |
|---|---|
| `step_update` with `step_type: agent_response` and `text_delta` | `text.delta` |
| first `step_update` of a `step_type: tool` step | `tool.started`; `run_command`, `view_file`, `write_to_file`, `replace_file_content`, `grep_search`, `read_url_content` and `search_web` under the card names of *Tool cards* (`antigravity/tool-calls.js`), a `call_mcp_tool` step after its server and tool (*Tool server*), any other tool under its own name with `tool_info.parameters` |
| first update of that step that carries `tool_info.parameters`, or its `DONE` or `ERROR` update | `tool.called` with the input |
| `DONE` or `ERROR` update of that step | `tool.completed` with `tool_info.output`, or `tool_info.error.message` as a failure; a `replace_file_content` edit carries its diff, starting at its `StartLine` |
| `result` with `status: SUCCESS` | `turn.completed` `succeeded` |
| `result` with `status: SUCCESS` and `denied_actions` after a turn without text | `turn.completed` `failed` with `error` `PermissionDenied`, naming the refused permissions and the fix |
| `result` with any other status, an `AGY_ERROR:` line on stderr during the turn, or an exit mid-turn | `turn.completed` `failed` |
| `user_input` and `system_message` steps, `command_result`, `subagent_info`, and the `step_type: unknown` step of an `ask_question` call (*Questions* below) | dropped |

agy streams no reasoning text, only `thinking_tokens`, so there is no `reasoning.delta`. It has no host approval channel either, so the process never emits `permission.requested` and `respondPermission` throws. A `PreToolUse` hook that answers `allow`, with or without `permissionOverrides`, does not lift the headless refusal (checked again with agy 1.4.2 on macOS, 2026-10-18: the hook ran and `run_command` still failed with "user denied permission").

**Questions.** agy's `ask_question` tool never reaches a stream-json client: agy 1.4.2 answers it itself, within about 25 ms, with "A1: User Skipped" (its log: `ask_question_manager.go] Auto-answering ask_question at step 2 with skipped=true`). This happens in every permission mode, `--dangerously-skip-permissions` included, the stream shows the call only as a `step_type: unknown` step without its question, and stdin takes nothing but `user` messages (any other `event` prints `warning: ignoring unsupported stream input message event`). agy does run `PreToolUse` hooks first, and a hook may take up to its `timeout` and `deny` the call with a `reason`, which the model reads as the call's result ("tool call denied by pre-tool hook: <reason>"). So the tool plugin (*Tool server*) also carries `hooks.json` with a `PreToolUse` hook on `ask_question` that runs `sh ask-question.sh` in the plugin folder, for up to a day: the script writes agy's hook input (`toolCall.args.questions[{ question, options, is_multi_select }]` and `toolSummary`) to `questions/<pid>.json`, then waits for `answers/<pid>.json` and prints it; it exits as soon as the folder is removed. `antigravity/question-hook.js` reads that folder every 250 ms while agy runs and the process emits `question.requested` (`q<index>` ids, the options as labels, `toolSummary` as the title, `custom` on, since agy takes write-in answers). `respondQuestion` writes `{ decision: "deny", reason }`, the reason starting "Not an error:" and listing each question with its answers, or saying the user closed the question without answering. A hook input that is no readable question gets `{}`, and agy goes on as without the hook. Checked against agy 1.4.2 on macOS, 2026-10-18 (`fixtures/ask-question-hook-input.json`, `fixtures/ask-question-answered.ndjson`): the hook ran in headless stream-json mode in both `default` and `--dangerously-skip-permissions`, the step waited for it, and the model answered with the user's pick; a hook past its `timeout` fails the step and the model goes on without an answer. The hook needs `sh`, so on Windows the plugin carries none and agy keeps skipping its questions there.

**Usage.** Each `agent_response` step carries `{ input_tokens, output_tokens, thinking_tokens, cache_read_tokens, total_tokens }` for its own model call, where input includes cache reads and output includes thinking. A turn's usage is the sum over its steps, with cache reads taken out of `input` and thinking out of `output`. Its `total` is the input plus output of the turn's last step with usage. The `result` usage is a running total for the whole conversation, so it is not used.

**Permission modes.** Headless agy refuses, without asking, every tool the mode does not allow, and the agent sees the refusal. Allow rules in agy's own `settings.json` apply in every mode. When a refusal leaves the turn without an answer, agy ends it with an empty `response`, lists the refusals in `result.denied_actions` (`[{ action: "command", display_name: "RunCommand" }]`) and prints `jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for…` on stderr. The process fails that turn with an error that names the permission and tells the user to switch the chat to `dangerously-skip-permissions` or add an allow rule such as `command(<target>)` under `permissions.allow` in `~/.gemini/antigravity-cli/settings.json`; before, the chat showed a turn with nothing in it. A turn that answered in text despite a refusal stays succeeded. Since agy can ask for nothing, a chat starts in `dangerously-skip-permissions`, the engine's default.

An account without `auto` gets `warning: --mode auto is not available for this account; continuing in the default mode.` on stderr and runs in `default`, where every command is refused. `agy --help` and agy's config files do not say which accounts have it, so `antigravity/auto-mode.js` asks agy itself: once per server start, when agy is signed in and not on Windows, it starts `agy --input-format stream-json --output-format stream-json --mode auto` in the temp folder with stdin closed. agy prints its `init` event and exits without a turn, so no model is called, in about 4 seconds; it does record an empty conversation. `auto` is listed only when that run exited 0 with `init` and without the warning. Until then, and on any failure or after 20 seconds, it is not listed. The `init` event's `permission_mode` reads `request-review` in `default`, `accept-edits` and unavailable `auto` alike, so it is not used. Checked against agy 1.4.2 on Linux (Pi 5) and macOS, 2026-10-18: both accounts print the warning. `agy -p "<prompt>" --mode auto` with separate arguments works; the adapter passes no `-p` and writes prompts to stdin.

| Mode | Flag | Lets agy |
|---|---|---|
| `default` | none | read the workspace; edits and commands are refused |
| `accept-edits` | `--mode accept-edits` | also edit files; commands still need an allow rule |
| `auto` | `--mode auto` | also run commands it judges safe; refuses irreversible actions. Linux and macOS only, agy 1.3.5 and later, and only for accounts that have it |
| `dangerously-skip-permissions` | `--dangerously-skip-permissions` | run every tool; the default and the full-permission mode |

`plan` is left out because a headless run approves its own plan and goes on to edit files, and issue 1181 reports writes in plan mode.

**Models.** `default` passes no `--model` and keeps the CLI's saved model and effort. Any other model passes its base id as `--model` and the effort as `--effort`. The list is what `agy models` shows for the signed-in account (*Model lists*); until a read lands it is `default` and `gemini-3.8-flash`.

**Install.** agy ships through an install script, which puts a native binary in `~/.local/bin/agy` or `%LOCALAPPDATA%\agy\bin\agy.exe`. The installer runs `curl -fsSL https://antigravity.google/cli/install.sh | bash` through `/bin/bash -c`, or `irm https://antigravity.google/cli/install.ps1 | iex` through PowerShell on Windows, for install and reinstall, and `agy update` to update (*CLI management*). The npm packages named `agy` and `antigravity-cli` are placeholders from other publishers.

**Sign-in.** `auth.status()` runs `agy models` and reports signed in when it lists a model; agy lists nothing without an account. It never reads stderr or credential files. agy has no login subcommand: `loginProcess()` starts its terminal UI, which opens the sign-in when no account is signed in, and presses Enter on its login method list to pick Google OAuth; agy then prints the Google link and asks to paste the authorization code. It signs out only inside its terminal UI, so `logout()` throws the step to take there.

**Not verified against a live agy:** the result text of `write_to_file`, `replace_file_content`, `grep_search`, `list_dir`, `read_url_content` and `search_web`, and whether agy reports a command's exit code. `fixtures/builtin-tools.ndjson` takes its parameters from calls agy 1.4.x stored in `~/.gemini/antigravity-cli/conversations` and leaves those results out; a live capture on 2026-10-19 failed because agy 1.4.2 answered no prompt there. The `view_file` summary comes from `fixtures/mcp-tool-call.ndjson` and a refused `run_command` from `fixtures/permission-denied-1.4.1.ndjson`, both recorded. Also not verified: whether `init` repeats on every turn, whether a prompt that is a slash command such as `/usage` ends with a `result`, and the fields of the `AGY_ERROR` line, of which only the prefix is read.

## The Codex adapter

`codex/` drives OpenAI's Codex CLI through `codex app-server`. It is written against the schema that codex-cli 0.163.0 generates with `codex app-server generate-json-schema --out <dir>`. After a Codex upgrade, regenerate the schema and compare it with `codex/protocol.js`.

**Process.** One `codex app-server` per session speaks JSON-RPC 2.0 over stdio: one JSON message per line, without the `jsonrpc` field. `CodexProcess` sends `initialize` with `clientInfo.name` set to `openchamber`, then the `initialized` notification, then `thread/start` with the session's `cwd`, `model`, `approvalPolicy` and `sandbox`, and a `config` that turns on `features.default_mode_request_user_input` (*Questions*) and adds the tool server when there is one (*Tool server*). Each prompt is a `turn/start` with the text and the reasoning `effort`. Codex runs one turn per thread at a time, so later prompts wait in the process until `turn/completed`. `codex exec --json` prints whole messages only, so it cannot stream text.

**Resume.** Codex writes a thread to disk with its first turn, and `thread/resume` on a thread without one answers "no rollout found". The process emits `engine.state` `{ threadId }` once Codex accepts a turn, and the next process calls `thread/resume` with that id and `excludeTurns: true`. When Codex answers "no rollout found", for example after `~/.codex/sessions` was cleared or under another `CODEX_HOME`, the process starts a new thread and stores its id. Earlier context is then lost to the CLI, while OpenChamber keeps its stored messages. Any other resume error fails the prompt.

**Events.**

| Codex message | Engine event |
|---|---|
| `item/agentMessage/delta` | `text.delta`; a blank line separates two agent messages that follow each other directly. A tool call or reasoning between them already makes them separate parts. |
| `item/reasoning/summaryTextDelta` | `reasoning.delta`; a blank line separates two summary parts that follow each other directly |
| `item/started` with a `commandExecution` item | `tool.started` and `tool.called` named `shell`, input `{ command, cwd }` |
| `item/started` with a `fileChange` item | `tool.started` and `tool.called`: one added file is `write` `{ path, content }`, one updated file `edit` `{ path }`, anything else `patch` `{ changes: [{ path, kind }] }` (`codex/tool-calls.js`) |
| `item/started` with an `mcpToolCall` item | `tool.started` and `tool.called` named `mcp__<server>__<tool>` (the tool server's own tools by their own names), input the call arguments |
| `item/completed` with a `commandExecution` item | `tool.completed` with `aggregatedOutput`; a status other than `completed` or a non-zero `exitCode` fails it, with `Exit code <n>` first; a declined command fails with a line saying so |
| `item/completed` with a `fileChange` item | `tool.completed` with `metadata.files` built from each change's `diff` (an added file's `diff` is its content), except for a `write`; a declined or failed change fails with a line saying so |
| `item/completed` with an `mcpToolCall` item | `tool.completed` with the result's text, or the error message when the status is not `completed` |
| `item/completed` with a `webSearch` item | `tool.started`, `tool.called` named `websearch` with the `query` (or the action's), and `tool.completed` with no text, since the schema leaves `results` opaque |
| server request `item/commandExecution/requestApproval` | `permission.requested` with tool `shell` and `{ command, cwd, reason }` |
| server request `item/fileChange/requestApproval` | `permission.requested` with tool `edit` and the paths and diffs of that item |
| server request `item/tool/requestUserInput` | `question.requested` with each question's `id`, `header`, `question` and `options`, and `custom` from `isOther` |
| `thread/tokenUsage/updated` | the usage of the next `turn.completed` |
| `turn/completed` with status `completed` | `turn.completed` `succeeded` |
| `turn/completed` with status `failed` or `interrupted`, or a rejected `turn/start` | `turn.completed` `failed` |
| `item/reasoning/textDelta`, `error`, `warning`, thread status, `item/completed` of other items, output deltas and every other method | dropped |

Codex sends raw reasoning text only with its `show_raw_agent_reasoning` setting, next to the summary, so reading the summary alone keeps reasoning from showing twice. An `error` notification with `willRetry: false` is followed by `turn/completed` with status `failed`, which ends the turn. Notifications from other threads, such as sub-agents, are dropped.

**Approvals.** Codex numbers its server requests per process, so each approval gets a UUID as `requestId`. `allow` answers `{ decision: "accept" }`. `deny` answers `{ decision: "decline" }`, and Codex goes on with the turn without the action. When Codex sends `serverRequest/resolved` first, a later reply, or answer to a question, is dropped. A `request_user_input` question gets a UUID the same way and is answered as in *Questions*. Every other server request, such as an MCP elicitation or `item/permissions/requestApproval` (sent only with Codex's `request_permissions_tool` feature, which is off), gets a JSON-RPC error so Codex does not wait on it.

**Questions.** codex-cli 0.163.0 offers `request_user_input` in its default collaboration mode only with `features.default_mode_request_user_input`, which it calls under development (it sends a `warning` notification, which the adapter drops). Without it the model has no question tool and, in plan collaboration mode, asks through an `agentMessage` with `delivery: "async"`. Checked against a signed-in codex-cli 0.163.0 on macOS, 2026-10-18 (`test/codex/turn-with-question.ndjson`): with the feature, `item/tool/requestUserInput` arrives even with `capabilities: null`, Codex waits for the answer and the model replies with it, and `{ answers: {} }` reads to the model as no answer.

**Usage.** `thread/tokenUsage/updated` carries the thread's running `total` and the `last` model response, and Codex may send the same numbers twice. A turn's usage is how far `total` grew during the turn. On a resumed thread, `total` minus `last` of the turn's first report is the starting point. Codex counts cache reads and cache writes inside `inputTokens` and reasoning inside `outputTokens`, so the adapter takes them out to keep the five counts apart. The turn's `total` is `inputTokens` plus `outputTokens` of its last report's `last`.

**Permission modes.** Each mode sets Codex's approval policy and sandbox on `thread/start` and `thread/resume`. The control bridge asks the user for every Codex approval, because Codex asks only when its policy says so. `on-request` is the default.

| Mode | `approvalPolicy` | `sandbox` | What Codex does |
|---|---|---|---|
| `read-only` | `on-request` | `read-only` | reads anything; asks before a write or a command that needs more |
| `untrusted` | `untrusted` | `workspace-write` | asks before every command except reads it knows to be safe |
| `on-request` | `on-request` | `workspace-write` | Codex's own default: works inside the workspace and asks to go beyond it, such as for network access |
| `never` | `never` | `workspace-write` | never asks; whatever the sandbox blocks fails and Codex is told |
| `full-access` | `never` | `danger-full-access` | never asks and runs without a sandbox; the full-permission mode |

**Models.** `codex/model-catalog.js` reads the models from the installed CLI: it starts `codex app-server` in the home folder, sends `initialize`, `initialized` and `model/list` (following `nextCursor` to the last page), and stops the process. `model/list` answers without a signed-in account. Each model's id is the `model` it reports, which `thread/start` takes, its name the `displayName`, and its efforts the `supportedReasoningEfforts`; the default is the model with `isDefault`. A model entry that does not parse is left out and the others are kept. codex-cli 0.163.0 lists eight models, `gpt-6.1-sol` the default; most offer `max` and `ultra` beyond `low` to `xhigh`, `gpt-6-luna` and `gpt-5.6-luna` stop at `max` and `gpt-5.5` at `xhigh` (`test/codex/model-list.ndjson`). `model/list` names no context window, so `limit` stays fixed until a turn reports `modelContextWindow`. OpenChamber keeps `medium` as the default effort, which every listed model offers; the CLI's own per-model default (`defaultReasoningEffort`) is not used.

The catalog never makes a request wait. The server starts the first read when it sets up the routes. Until a read succeeds, the catalog serves the stored list (*Model lists*), else the fallback list in `codex/model-catalog.js`, what 0.163.0 listed, with the four efforts every model there accepts; after that it serves the list of the last successful read. A failed read, an empty list or no answer within 15 seconds keeps what was served and logs a warning. Without the CLI nothing is read. Serving the catalog checks in the background, at most every 30 seconds, which `codex` binary and version the installer finds; a different one, or 10 minutes since the last read, starts a new read. One read runs at a time. A Codex installed while the server runs is read at the first check after it appears.

The model goes on `thread/start` and `thread/resume` and the effort on each `turn/start`. A change to either, or to the permission mode, reaches Codex with the next prompt, which replaces the idle process (*Session settings*). A model that disappears from a newer list can no longer be picked, but a chat already on it keeps prompting on it.

**Install.** `npm install -g @openai/codex@latest`. On Windows the npm launcher is `codex.cmd` in `%APPDATA%\npm` and runs through `cmd.exe`. The launcher picks the native binary for the platform and puts its bundled tools on PATH, so the adapter always runs the launcher. On macOS and Linux the adapter checks `/usr/local/bin`, `/opt/homebrew/bin`, `/usr/bin`, `~/.local/bin` and `~/.npm-global/bin`, then the login shell's PATH. The version comes from the package's `package.json` next to the launcher, or from `codex --version`.

**Sign-in.** `auth.status()` runs `codex login status`. Exit code 0 means signed in, and the line on stderr tells ChatGPT from an API key. That line ends in a masked key, so the adapter keeps only the method and never returns or logs the line. It never reads `auth.json`, since Codex can keep credentials in the OS keyring. `loginProcess()` is `codex login --device-auth`, which prints a link and a one-time code and finishes by itself once the code is entered on the page. `logout()` runs `codex logout` and reports a failure with the step to take.

**Enterprise mode.** A Codex session sends its conversation to OpenAI, the session's own provider, the way a Claude session sends it to Anthropic. Signing in through this server is refused in enterprise mode, as for every engine, but a Codex the user signed in to from a terminal still runs. Whether enterprise mode should turn the Codex engine off entirely is a question for the maintainer.

**Not verified against a live, signed-in Codex:** a full turn, because Codex was not signed in where the adapter was written. The handshake, `model/list` (`test/codex/model-list.ndjson`), `thread/start`, `thread/resume` of a missing thread and a failing turn were recorded from codex-cli 0.163.0. The text, reasoning, tool, approval and usage messages in `test/codex/turn-with-tools.ndjson` were built from the generated schema and validated against it. `test/codex/turn-with-shell-and-patches.ndjson` is a turn recorded from a signed-in codex-cli 0.163.0 on macOS, 2026-10-19, with the paths, host and account lines taken out: two commands that succeed, one that exits 1, one added file and one updated file. Not recorded: a deleted or moved file (the adapter assumes a deleted file's `diff` is its old content), `item/commandExecution/outputDelta` (live output is not streamed; the command's output arrives when it ends) and a `webSearch` item. Whether cache writes are part of `inputTokens` is assumed; OpenAI models report none.

## The Claude adapter

- Permission prompts use `--permission-prompt-tool stdio`, which sends each one as a `can_use_tool` control request. `--permission-prompts host` denies them silently in this mode, so `manual` never asked. A denial carries a message the agent reads.
- `AskUserQuestion` comes the same way, with `requires_user_interaction: true`, in every mode, `bypassPermissions` included. The adapter emits it as `question.requested` instead of a permission (*Questions*). Allowing it without `updatedInput.answers`, which a permission reply did, gives the model "The user did not answer the questions."; with them it reads `Your questions have been answered: "Which color?"="Blue"`. Checked against Claude Code 2.1.302 on macOS, 2026-10-18.
- `ExitPlanMode` stays a permission request, with the plan as its `summary`, which the permission card shows and the notification names. Allowing it ends plan mode: Claude switches itself to `default` and goes on to implement.
- The permission mode switches in a running process through the `set_permission_mode` control request; Claude answers with a `control_response` (`success`, or `error` with the reason), which `ClaudeProcess.sendControlRequest` waits for up to 5 seconds. Claude reports `manual` back as `default`. What each mode does, as the composer describes it: `manual` asks before edits and commands, `acceptEdits` edits files without asking and asks before other commands, `plan` reads and plans without changing anything, `auto` lets Claude's classifier allow safe actions and block risky ones, `dontAsk` refuses every tool not allowed in the user's settings, and `bypassPermissions` runs every tool without asking.
- The `result` usage adds up every model call of the turn. Each call's final counts arrive in its `message_delta` stream event (from `--include-partial-messages`), and a count that event leaves null keeps the call's `message_start` value. The `assistant` messages carry only the counts from the call's start, before the output was written. The turn's `total` is input, cache read, cache write and output tokens of its last call. A subagent's calls name the call that runs them (`parent_tool_use_id`) and are left out. In a turn recorded with Claude Code 2.1.302 that read three files one at a time, the counts added up to 146,232 tokens and `total` was 36,705. A turn without a finished call reports no `total`.
- A background task (a `Bash` call with `run_in_background`, a background subagent) that finishes after the turn's `result` makes Claude begin a turn of its own: a `task_notification` system message, an `init`, then a model call and a `result`, with no echoed prompt. The adapter emits `turn.started` when the conversation's first model call (`message_start` with no `parent_tool_use_id`) comes while no turn is open, and when a prompt is echoed then. A turn opened this way counts as open for `prompt.merged`. Recorded with Claude Code 2.1.303 on macOS, 2026-10-22: a background `sleep`, then an `AskUserQuestion` answered, `result` "ANSWER: Red", and 11 seconds later the notification turn with `result` "NOTIFIED".
- Claude keeps its transcript under OpenChamber's session id. It refuses `--session-id` for an id it already has and `--resume` for one it has never seen. The process emits `engine.state` `{ transcript: true }` on Claude's first `init`, and every later process passes `--resume`. Sessions stored before that flag existed resume when an earlier turn has a stored answer.
