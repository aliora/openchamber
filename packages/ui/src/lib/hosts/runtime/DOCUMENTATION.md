# Host runtimes

One runtime per OpenChamber host the window talks to: its transport, its SDK client, its connection status and its own copy of every per-host store. Shared code keeps calling singletons (`opencodeClient`, store hooks); those singletons are facades that find the right host at call time.

On web, VS Code and hosted mobile the registry holds exactly one host, the window's active runtime. On the Electron local page and in the Capacitor app (see *Several hosts at once*) every saved host is registered beside it, gets its own sync engine, and a host switch only moves the focus. The transport and the SDK client are per host already: the global `runtime-*` functions reach a transport object instead of module state, and `opencodeClient` is a facade over the resolved host's `OpencodeService`. The stores the event reducer writes are per host too, and so are the catalog, source-control, guest, file and terminal stores that serve the focused host and the session, directory, project, space and config stores the window works through (see *Per-host stores*).

## Which host a call reaches

`resolveHost()` returns the ambient host while one is set, else the focused host.

- **Focused**: the host the window shows. `registry.focus(id)` changes it. The first registered host takes the focus; unregistering the focused host hands it to the first remaining host. `focused()` throws only when the registry is empty.
- **Ambient**: `runWithHost(host, fn)` (or `host.run(fn)`) sets the host for the synchronous part of `fn` only. It is restored when `fn` returns or throws, nested calls restore the outer host, and it never reaches code after an `await`, a `.then` callback or a queued microtask.

Async code names its host instead of relying on the ambient one:

```ts
const host = resolveHost();
const result = await host.client.someCall();
if (host.disposed) return;
host.run(() => useSomeStore.getState().apply(result));
```

## Registry

`register(savedHost, credential, parts?)` builds a runtime keyed by the descriptor's `runtimeKey` (`HostId` is the runtime key) from `parts` when given, else from the registry's `createParts`. Registering an id that exists replaces that runtime: the old one is disposed and the focus stays on the id. When the new runtime keeps the old one's `storeScope`, the old runtime forwards to it: its `transport`, `client`, `descriptor` and `status` read the new runtime's and its `run` makes the new runtime ambient. Stores, values and module code that captured the old runtime object (a store factory's `host`, a terminal socket's dependencies) therefore reach the new transport, while `disposed` still reports the old runtime as gone. `unregister(id)` disposes the runtime. Disposing marks `disposed`, closes the transport once, and leaves the runtime's stores to garbage collection. A runtime's `storeScope` is what its per-host stores and values are kept under: the parts may hand one in (`HostRuntimeParts.storeScope`), otherwise every runtime gets its own, so a replaced runtime starts with fresh stores. `list()` keeps its array identity until the registry changes. Every change (register, unregister, focus) notifies `subscribe` listeners.

`status` holds the host's `HostConnection`, `connecting` until a connection supervisor owns it.

With several hosts, `app-host.ts` follows a focus change that no switch made: when the focused host leaves the registry, the focus goes to the first remaining host and `app-host.ts` calls `switchRuntimeEndpoint` with that host's endpoint, so the runtime events fire and `getRuntimeKey()` names the new focus.

## Facades

`createFocusFacade(blueprint, resolve)` returns a plain object, not a `Proxy`, with one own property per member of `blueprint` and of its prototype chain below `Object.prototype` (`constructor` excluded). `blueprint` is any value of the facade's type, typically the class's `prototype` (`createFocusFacade(OpencodeService.prototype, () => resolveHost().client)`); it is also the facade's prototype, so `instanceof` against its class is true. Its members are read once, when the facade is built.

- A method becomes an own function that calls `resolve()` when it is called and runs the method on that object, so an async method keeps working against its original host after the focus moves. The function is the same on every read (`facade.method === facade.method`).
- Any other member (a getter, a data field) becomes an accessor that reads from and writes to `resolve()` at the moment of access; a method value read this way is bound to the object it was read from.
- `in` reports the blueprint's members whatever the resolved object holds. A name the blueprint lacks (an instance field set in a constructor) is not forwarded: it reads as `undefined` and a write lands on the facade.
- Methods are own data properties so that test spies work: Bun's `spyOn` and an assignment (`facade.method = fake`) replace the facade's function and intercept the calls made through the facade, not the resolved object's own calls to `this.method`. Restoring puts the forwarding function back.

Every call or access is one `resolve()` call: O(1).

## Per-host stores

`defineHostStore(name, factory)` returns a zustand bound-store lookalike whose state lives per host. `factory(host)` runs once per store scope, on first use, under `host.run`.

| Access | Store reached |
|---|---|
| `getState`, `getInitialState`, `setState` | `resolveHost()`'s store |
| `subscribe` outside `runWithHost` | The focused host's store; on a focus change the listener moves to the new host's store and is called once with the new and the previous host's state |
| `subscribe` inside `runWithHost` | That host's store, for good |
| The hook (`useX()`, `useX(selector)`) | The `HostScopeContext` host when set, else the focused host; re-renders on focus change |
| `forHost(id)` | That host's store, typed as the factory made it (a persisted store keeps its `persist` API); throws for an unknown id |
| `subscribeEveryHost(listener)` | Every host's store, those already made and those made later; the listener is called with the host's state, the previous state and the host, with that host ambient |

Each access is a registry lookup and a `WeakMap` lookup keyed by the runtime's `storeScope`: O(1).

`defineHostValue(factory)` returns a reader of a plain per-host value (`readValue()` gives `resolveHost()`'s value, `host.run(readValue)` a given host's). Module bookkeeping that sits beside a host store, such as revisions, generations and caches, lives in one so it follows the same host as the store.

A store factory gets its host; module functions resolve the host at call time. Code that awaits captures the host first and comes back to it with `host.run(...)`; a load that finishes after its host left the registry (`hostStoresLive(host)` is false) commits nothing.

### Which stores are per host

The stores the event reducer writes are host stores: `useGlobalSessionsStore`, `global-session-status`, `global-blocking-requests`, `background-shells`, `session-ordering`, `session-activity-timing`, `global-sync-store`, `permissionStore` and `useStreamingStore`, and `sync-refs` keeps its child-store manager, directory and session index per host (`defineHostValue`). The sync engine's own bookkeeping is a `defineHostValue` too (`sync/sync-host-state.ts`, see `sync/DOCUMENTATION.md`). The event pipeline is given its host's transport (`runtimeTransport`) for the WebSocket address, its URL token and the socket. `useAuthSessionStore` reads the session state of its host's transport: each transport's fetch reports its own 401s and probes through itself. The parent lookup that `sync-context.tsx` hands `setSessionParentResolver` reads the global sessions store through its facade, so it answers for the host the status code is working for.

`messageQueueStore`, `useAutoReviewStore` and `useMultiRunStore` stay single stores whose entries carry a runtime key; a runtime switch no longer resets them. `useSessionFoldersStore` stays a single store too, but it holds only the active runtime's folders, so a runtime switch still loads the new runtime's folders into it (`resetForRuntimeSwitch(runtimeKey)`).

### Stores that serve the focused host

The catalog, source-control, guest, file and terminal stores are host stores too, created the first time something reads them for a host: `useCommandsStore`, `useAgentsStore`, `useMcpStore`, `useSkillsStore`, `useQuotaStore`, `useEngineReadinessStore`, `useEngineControlsStore`, `useAgentMemoryStore`, `useGitStore`, `useGitIdentitiesStore`, `useSourceControlAuthStore`, `useChangeRequestContextStore`, `useGitHubPrStatusStore`, `useLinearAuthStore`, `useGuestsStore` (seeded with its host's id as `runtimeKey`), `useGuestOauthStore`, `useFileSearchStore`, `useFilesViewTabsStore` and `useTerminalStore`. `repositoryBindingOwner` is a facade (`createFocusFacade`) over one `RepositoryBindingOwner` per host. The bookkeeping beside each store (generations, in-flight maps, load caches, timers) is a `defineHostValue` of the same host.

- **Which host an action works for**: the store's factory gets its host. Every read or write an action sends, and every other store it reads, goes through `host.run(...)` (`hostRuntimeFetch(host, ...)` for `runtimeFetch`), before and after each `await`; its `set` is its own instance's. A load that finishes after the focus moved therefore commits into the host that started it. Module functions that start work (`loadGuestCatalog`, `refreshSkillsAfterOpenCodeRestart`, `reloadOpenCodeConfiguration`, `waitForOpenCodeConnection`, the terminal API) capture `resolveHost()` when called. Guards that asked whether the runtime key changed under a request ask `hostStoresLive(host)` instead; the git store keys its requests by its own host's id, and the git identity, quota, source-control auth and pull request keys, like the chats-root cache of `lib/chatDirectories.ts`, by `currentHostKey()`: the ambient host's id, else the window's key.
- **No work in the background**: these stores start no work for a host the window does not show. `refreshStoresForCatalogKind` (`stores/catalogRefresh.ts`) re-reads only for the focused host; a catalog event for a background host marks that kind (and its locations) stale on the host, and the next focus of that host re-reads them once. An MCP status announcement for a background host (`useMcpStore.refreshIfHeld`) waits the same way. Both go through `runWhenFocused`.
- **Terminals**: `lib/terminalApi.ts` keeps its socket per target per host. When a host leaves the focus its sockets close and stop reconnecting (`TerminalTransport.suspend`); its subscribers, tab list and scrollback projections stay. When it is focused again each socket reconnects and attaches every terminal still subscribed (`resume`), and the server's snapshot replaces the projection. The sockets of a host that leaves the registry are disposed. `disposeTerminalInputTransport()` disposes the resolved host's sockets.
- **Persistence**: the commands, agents and skills stores keep one shared key for the selected item. `useFilesViewTabsStore` and `useGitHubPrStatusStore` keep their single key, whose records are already keyed by runtime; every host instance writes through one shared storage that keeps, per runtime snapshot or per entry, whichever copy is newer, so two hosts writing in turn never drop each other's records. `useTerminalStore` persists per host (`terminal-store:<hostId>`, session storage); the host of the current runtime adopts the old shared key once.
- **Runtime switch**: a switch to another runtime key gives the new host fresh instances, which is what the resets in `apps/runtimeEndpointReset.ts` used to do; the previous host's instances go with its runtime. An endpoint change that keeps the key resets them explicitly (`resetSameHostFocusedStores`), terminal sockets and tabs included.

### Stores of the window's own work

The stores the window works through are host stores as well: `session-ui-store`, `useDirectoryStore`, `useProjectsStore`, `useProjectContextStore`, `useSpacesStore`, `useSpaceArchivesStore`, `useConfigStore` and `useSessionPinnedStore`. Beside them, per host (`defineHostValue`): the spaces bookkeeping (progress revisions, the reset generation, custom-provider reads), what a space creation chose (`space-model-access`) and the requests waiting for a space (`space-creation`), the archives read, the directory store's home lookup, the session store's guessed selection, the config store's `initializeApp` run and the pin overlay and click queues.

- **Actions run on their host**: these stores build their state with `bindHostActions(host, state)`, which wraps every function in the state so its synchronous part runs with the store's host ambient: the SDK facade, `runtimeFetch` and every other store reach that host. After each `await` an action names its host again (`host.run(...)`); its own `set` and `get` are its instance's. A load that finishes after the focus moved therefore lands in the host that started it. Guards that asked whether the runtime key changed under a request ask `hostStoresLive(host)`; the config store's context carries its host (`captureConfigRuntimeContext`), and the load caches beside it (freshness, stale marks, in-flight loads, agent load errors: `configLoads`) are a host value. A same-key endpoint change, or a switch with one host, clears the resolved host's caches and bumps the generation; a focus switch between hosts clears nothing, so a load still running on the host left behind lands there.
- **Listeners follow every host**: a listener that saves or derives per host subscribes with `subscribeEveryHost`, not `subscribe`, which hears the focused host only: the global session snapshot and managed-chats save, the pin set, the move of device-local pins into session metadata and the session store's worktree map.
- **Persistence per host**: `config-store:<hostId>` (the host whose id the old shared `config-store` blob names adopts it once; the blob is then removed), `permission-store:<hostId>` (the old shared blob goes to the host its `legacyRuntimeKey` names, or to the first host when it names none), `oc.session-activity.v1:<hostId>` (stamped for every host when the page hides), session caches and the global snapshot under `currentHostKey()`. Pending session-cache writes of every host flush together; a write whose host left the registry is dropped. The projects cache keeps its key, namespaced by the API base URL when the store is made for the window's current key (a same-key endpoint change reads it again), else by the host's id, so a background host never reads or writes the focused host's cache. Settings reads and debounced writes (`lib/persistence.ts`) capture the host with their context and are sent through it; the GET cache, the in-flight read, a pending write, the mutation overlay and the values its server is known to hold (which drop redundant writes) belong to that host, so writes of two hosts never merge, one host's read is never served to another and one host's known value never suppresses a write to another. With several hosts a write is delivered while its host is registered, whatever the focus does meanwhile; with one host it is also dropped once the runtime switched, since the window transport then serves the new runtime. Only a document of the focused host reaches the window: `applyServerSettings`, the `openchamber:settings-synced` event (which the projects store applies to the focused host) and the local mirrors; a background host's save is written to its server and its answer is not applied. `directory-store:<hostId>` and `projects-store:<hostId>` are devtools names.
- **Runtime switch**: before a switch to another key (`subscribeRuntimeEndpointWillChange`, `prepareAppForRuntimeEndpointChange`, from `installRuntimeEndpointReset` and `MobileApp`) the host being left remembers its selection, draft, worktree maps, live status and open transcript (`rememberForRuntimeSwitch`), keyed by its id. The new host's session store starts from what is remembered for its id. After the switch `resumeAfterRuntimeSwitch(previousKey)` points the window at it: the remembered directory, else a forgotten directory when the previous host was a real one, and the active session the sync layer tracks. A new host's directory store starts as a copy of the window's directory, the focused host's last state, which keeps a cold launch through a disconnected key on the directory the window started with. With several hosts every host starts from its own stored last directory and home (`lib/hostDirectoryStorage.ts`: `lastDirectory:<hostId>`, `homeDirectory:<hostId>`, written by its directory store and by its settings read), else the forgotten directory (`/`, home not ready), and the home is resolved when the window first focuses it. The window-wide `lastDirectory` that older builds wrote for whichever host was focused is never read on the multi-host desktop page (`isDesktopMultiHostPage()`), whose window host is created before the flag is set; the phone starts on the transient `url:default` host, which leaves with that boot value. Single-host surfaces keep that one key. Focusing a host whose home is ready resolves nothing. An endpoint change that keeps the key keeps these stores and resets them as every switch used to (`resetSameHostUiStores`).

### Importing the bindings

Stores import `defineHostStore` and friends from `host-bindings.ts`, never from `app-host.ts`: `app-host.ts` pulls in the SDK client and `runtime-switch`, which many tests replace with `mock.module` stubs that list only a few exports, and the client imports stores itself. Host stores and the registry build their stores with `createStore` from `zustand/vanilla` and the hook with `useStore` from `zustand/react` for the same reason: one test replaces `zustand` with a stub that has only `create`.

Until `app-host.ts` has loaded (a test whose SDK client is a stub), `hostRegistry` holds a single standalone host on the window transport with no SDK client. Once `app-host.ts` loads, the next registry access replaces it with the active runtime, as a runtime switch would.

## The single host today

`app-host.ts` keeps `hostRegistry` equal to the window's active runtime:

- On first use, and whenever the runtime key no longer matches its entry (`initializeRuntimeEndpoint` at boot dispatches no event), the entry is rebuilt from `getRuntimeKey()` and `getRuntimeApiBaseUrl()`.
- From first use on, every `switchRuntimeEndpoint` rebuilds the entry synchronously on the changed event, even when the key stays the same (a sign-in or a relay-to-direct swap). The previous runtime is disposed at once, so code holding it sees `disposed`. A switch to another key unregisters only the previous window entry (on the first rebuild, every entry present, such as the standalone placeholder); hosts registered beside it stay.
- The entry's store scope is kept while the runtime key stays the same, so a same-key rebuild keeps the host's stores (a relay-to-direct swap on mobile keeps the session list, statuses and pending requests as it did before). A new key gets a fresh scope: the new host's stores start empty, which is what the reset on a runtime switch used to do, and the previous host's stores go with its runtime. Where a same-runtime endpoint change still resets the app (`resetAppForRuntimeEndpointChange` with an unchanged key), it resets these stores explicitly.
- The entry's transport is the window transport, borrowed: disposing the entry closes nothing, so the rebuild on every switch keeps the window's tunnel and URL token. Its client is the window's `OpencodeService`, created on first read of `client` over that borrowed transport with `getRuntimeKey` as its runtime key, and the same instance for every rebuild: its directory, caches and in-flight work survive a switch as they did when it was a module singleton. Its credential reads the window transport's bearer token and extra headers.
- The descriptor's id and label are the runtime key; `kind` is `relay` while a relay tunnel is active, `local` for the `local` key, else `direct`. `displayUrl` is redacted.

This is the same on web, Electron, VS Code, hosted mobile and Capacitor mobile: every surface goes through `runtime-switch.ts`.

## Several hosts at once

With the multi-host runtime on, `SyncProvider` (`sync/sync-context.tsx`) loads `saved-host-runtimes.ts` and `runtime-hosts-monitoring.ts`, calls `savedHostRuntimes.ensure(hostsApi)` with the `HostsAPI` the app passes (`App.tsx`, `MobileApp.tsx`), installs the runtime hosts feed and starts it with the same API (`hostsMonitoring.ensure`), so every host's connection is supervised, and the focused one's offline marker current, before any sidebar mounts. The flag is read once per `SyncProvider` mount; off, nothing here runs and the registry holds the window host alone.

- **Which hosts**: every saved host except the one the window transport serves (`windowHostKey()`, matched with `isActiveHost`), keyed by its `runtimeKey`. A host the window switches to keeps its runtime and its stores; only the focus moves.
- **Parts**: a transport of its own (`createRuntimeTransport` with `bootInjection: false` and the page's native fetch, never the runtime fetch bridge), configured from the endpoint: `local` and `direct` by address, `relay` through its own tunnel (API base `location.origin`, as a relay switch uses), `multi` by its direct address. The credential is read once before registering, so the token and extra headers are set before the first request, and read again for every request's token. The SDK client is `new OpencodeService({ transport, runtimeKey: () => runtimeKey })`.
- **Changes**: the list is read again on every `ensure` with a new API, on `refresh()` and after each window switch. A failed read keeps the registered hosts; `unsupported` or a host removed from the list unregisters it. A host whose endpoint changed is registered again on its store scope, so its stores stay and follow the new transport (see *Registry*). A listed host that is already registered (a switch or a background connect got there first) is taken over as it is, so it leaves the registry with the list.

## Switching hosts

`switchRuntimeEndpoint` keeps its contract: the will-change and changed events fire with the same detail, and `getRuntimeKey()` and `getRuntimeApiBaseUrl()` report the new host afterwards, so the window key follows the focus. Between the two events it asks the router `app-host.ts` installs (`routeRuntimeEndpoints`) where the endpoint goes.

- **One host (web, VS Code, hosted mobile)**: the window transport is reconfigured and the window entry rebuilt, as described in *The single host today*.
- **Several hosts**: a switch to the window host's key reconfigures the window transport only when its endpoint changed; a switch to any other key updates that host (its transport reconfigured and its SDK client reconnected when the endpoint differs, else nothing) or registers it with parts of its own (`host-parts.ts`), then focuses it. The window globals are written only for the window host, so another host never inherits its token. A transient host the focus leaves (`url:default`, `mobile-disconnected`) is unregistered. The window's `OpencodeService` keeps the window host's key as its runtime key, so a send on that host finishes after the focus moves.

The helpers of `app-host.ts` name the host they act on:

- `focusRegisteredHost(id)` switches to a registered host with the endpoint its transport already has (the window host's own endpoint for the window host), so the focus moves without a probe or a reconnect. False for a host that is not registered or with one host.
- `registerHostEndpoint(id, endpoint)` puts a host beside the others without focusing it: a new host gets parts of its own, a registered one is reconfigured and its client reconnected in place, so a LAN⇄relay swap of a background host keeps its runtime, stores and engine. False for the window host and with one host.
- `applyHostEndpoint(id, endpoint)` changes the endpoint of a registered host: through `switchRuntimeEndpoint` when it is focused (the same-key change the events describe), else through `registerHostEndpoint`.
- `adoptRelayTunnelForHost(id, descriptor, tunnel)` hands a probe's live tunnel to the host it was opened for: its transport adopts it when the host is registered, else it waits for that host's parts, so a switch to another host never replaces the focused host's tunnel. With one host it goes to the window transport, as `adoptRelayTunnel` did.

`apps/runtimeEndpointReset.ts` resets the app only where a host's stores are new: on a different key with several hosts it disables multi-select, cancels git refresh timers, resets the walkthrough, points the session folders at the host (read from the server only the first time a page shows that host), closes a guest page and re-reads the settings (`focusAppOnHost`; the settings stay one window-wide copy, so the focused host's are read again), and neither reconnects a client nor resets a store. A same-key credential change resets as before. App and `MobileApp` no longer remount `SyncProvider`; The chat column (`MainLayout`) and the phone's chat view (`MobileApp`) stay mounted across a focus move: their `ErrorBoundary` takes the focused host id as `resetKey`, so a caught error clears on a focus move without remounting a working chat. Per-host state inside the chat follows its session key, which includes the runtime key. The single-host `SyncProvider` follows the runtime key itself and makes new engine parts for a new key.

`FocusedHostGate` (`components/auth/`) wraps the chat column (`MainLayout` on the desktop, `MobileApp` on the phone). On a host other than the window host it shows `SessionAuthGate` in `embedded` mode, inside the chat column, while the host's connection is `auth-required` or its transport's auth session is `reauthenticating`; every other host keeps working. While the host's connection is `connecting`, `backoff` or `relay-limit` and its session list has never loaded, the column shows an offline marker instead of the chat: the host's name, connecting / offline / not responding / relay limit, and Try again (`hostsMonitoring.refresh()`) except while connecting. A host with a loaded session list keeps its chat and shows the same state as a small pill over it (`data-host-offline-indicator`). A focused host that does not answer is therefore never an empty chat; once it is `live` the marker goes. The gate renders the same element shape for every host, the window host included, so a focus move never remounts the chat. `incompatible` keeps the chat. The outer `SessionAuthGate` of `main.tsx` follows only the window host (`windowHostKey()`) when several hosts run. `CodeCliCompatibilityGate` remembers each host's verdict: focusing a host it already checked sends nothing and opens the setup wizard again only for an incompatible one.

## Host connections and sidebar rows

`runtime-hosts-monitoring.ts` gives every registered runtime a supervisor (`host-connection-supervisor.ts`). While the host's event stream is connected (its `useConfigStore.isConnected`) the connection is `live` via `stream` and nothing is probed. Otherwise the supervisor asks `GET /api/sessions/status` through the host's own transport: an answer makes it `live` via `poll` and asks again after 10 s (60 s hidden); 401/403 is `auth-required`, 404 `incompatible`, the relay limit `relay-limit`, each followed by the 5 minute wait; any other failure is `backoff` from 1 s doubling to 30 s while the page is visible and 5 minutes while it is hidden or offline. The page becoming visible, going online, or a runtime endpoint change wakes every supervisor.

A probe still waiting when the event stream comes up is aborted and the host is `live` via `stream`; a probe that failed while the stream came up never marks the host `backoff`. Before the first probe, and again before each retry after a failure, a supervisor runs the connector `provideHostConnector` set (none: nothing). A connector failure is swallowed; the probe reports the host. `hostsMonitoring.refresh()` (the sidebar's Refresh, the phone's resume) makes every supervisor run it again at once, the live ones included. The first time a host other than the focused one is `live`, the feed reads its `/api/config/settings` through its own transport into its projects store (`synchronizeFromSettings` without adopting an active project), so its row groups by its real projects; a failed read tries again on the next `live`.

The feed fills `useHostsStore` with one row per monitored saved host other than the focused one: the descriptor from `savedHostRuntimes.listed`, the runtime's connection, and `createHostSnapshotProjector()` over the host's global sessions, statuses, pending requests and, once its projects store has a server snapshot, projects. A host without a runtime yet reads `connecting` with a `loading` list; a host whose list load failed keeps its sessions under `error`, never an empty list. `watchedTransports()` and `transportFor()` hand out `hostTransportOverRuntime` adapters of the hosts' runtime transports. There are no summary monitors: every row, In work included, comes from the hosts' own stores.

## Desktop and phone

- **Desktop**: the main window always shows the app's own UI, on Local (or, without a local server, the loopback host that stands in for it) as the window host. The shell's boot outcome names `initialFocusHostId`, the last focused host, and `focusInitialDesktopHost()` (`lib/desktopHostActions.ts`) focuses it once the app has mounted. `openchamber://host/<id>` reaches the page as `openchamber:focus-host` (`subscribeDesktopFocusHost`), and `switchToDesktopHost(id)` focuses: a registered host as it is (`focusRegisteredHost`), a saved host at the address of a window keyed `url:<address>` as the window host (one runtime per address, never a second one beside it), otherwise Local at its origin, a relay host direct first with the tunnel as fallback, a direct host at its address. Every focus change is written back as the last focused host (`persistFocusedDesktopHost`). A window opened for one host (`explicitRuntime`, a relay host id) stays single-host.
- **Phone**: the cold-launch auto-connect focuses the most recent saved device and connects every other one beside it in parallel (`connectOtherMobileConnections`: each device's candidates probed, the answering transport registered with `registerHostEndpoint`, a relay probe's tunnel handed over). The phone's connector (`connectMobileHost`) does the same for one device whenever its supervisor asks, so a background device moves between LAN and relay on its own. A focused device that stops answering after resume stays focused and offline in place, and one whose token was refused or whose relay is over its limits stays focused too: its supervisor marks it `auth-required` or `relay-limit` and `FocusedHostGate` shows the sign-in or the relay notice in its chat. `mobile-disconnected` is used when nothing else is saved, when a single-host phone's token was refused or its relay is over its limits (the connect screen is the way to sign in again), when a cold launch finds the token refused, and when the user cancels. Removing the device the window is on focuses the most recent remaining one.

## Transport

`RuntimeTransport` is everything one host is reached through:

```ts
type RuntimeTransport = {
  readonly endpoint: RuntimeTransportEndpoint | null; // the last endpoint `reconfigure` applied
  readonly urls: RuntimeUrlResolver;          // api, sse, websocket, assets, with this transport's URL token
  setUrls(resolver): void;
  configureUrls(config): RuntimeUrlResolver;  // built with this transport's auth unless config.auth is given
  readonly auth: RuntimeAuth;                 // bearer token, extra headers, URL token, proactive refresh
  readonly relay: RuntimeRelay;               // this transport's tunnel, if any
  fetch(input, init?): Promise<Response>;     // runtimeFetch semantics, own read coalescing
  openWebSocket(url, protocols?): RelayTunnelWebSocket;
  reconfigure(endpoint): void;                // what a switch does: URLs, headers, token, tunnel, URL-token mint; bumps epoch
  readonly epoch: number;
  close(): void;                              // closes the tunnel, stops the URL-token timer
};
```

`createRuntimeTransport({ bootInjection, fetch, createTunnel })` builds one. `bootInjection` lets the transport fall back to the window's injected client token, runtime headers and API base URL (`__OPENCHAMBER_CLIENT_TOKEN__`, `__OPENCHAMBER_RUNTIME_HEADERS__`, `__OPENCHAMBER_API_BASE_URL__`); only the window transport sets it, so another host never borrows the boot credentials. `fetch` is the network fetch the transport sends direct requests and URL-token mints with.

- **Window transport**: `windowRuntimeTransport()` is created on first use with the page's `fetch` (read at call time, so the fetch bridge still sees runtime requests) and `createRelayTunnelClient`. `switchRuntimeEndpoint` calls its `reconfigure`; the window globals it writes stay for boot injection.
- **Global functions**: `runtimeFetch`, `getRuntimeUrlResolver`, the `runtime-auth` getters and setters, the `*RelayTunnel*` functions and `openRuntimeWebSocket` reach `currentRuntimeTransport()`: the ambient host's transport inside `runWithHost`, else the focused host's transport, else the window transport. The page's `window.fetch` bridge resolves it per call the same way.
- **Shared by every transport**: the local-origin URL token (`setLocalRuntimeUrlAuthToken`, `getLocalRuntimeUrlAuthTokenSync`, `refreshLocalRuntimeUrlAuthToken`) for the Electron realtime proxy, which stays module state. Clearing any transport's URL token clears it too, as before.
- Two transports never share requests, read coalescing, URL tokens or tunnels; closing one leaves the other open.

`lib/runtime-auth.ts`, `lib/runtime-url.ts`, `lib/runtime-fetch.ts`, `lib/relay/runtime-tunnel.ts` and `lib/relay/runtime-socket.ts` keep their exports and only delegate. The implementations sit in the `transport-*.ts` files because many test files replace those five modules with `mock.module` stubs that list only the functions they use; a transport built from the stubbed modules would fail to load in those tests.

The global functions do not import `app-host.ts`: it pulls in the registry, `runtime-switch` and the whole SDK client module, which most of the app imports through these low-level modules. `app-host.ts` calls `followFocusedHostTransport(() => hostRegistry.focused().transport)` when it loads instead. Until then (a module that never loads the client) `currentRuntimeTransport()` falls back to the window transport, which is the focused host's transport anyway while the registry holds the single window host.

`hostTransportOverRuntime(runtime)` in `lib/hosts/host-transport.ts` gives a monitor the `HostTransport` shape over a runtime transport, so a monitor and a runtime can share one host's transport. It neither closes the runtime transport nor hands out its tunnel.

## SDK client

`new OpencodeService({ transport, runtimeKey })` is one host's OpenCode client: every request, the generated `@opencode/client` included (`createRuntimeOpencodeClient({ baseUrl, transport })`), goes through `transport.fetch`; its base URL is `transport.urls.api('/api')`; relay checks read `transport.relay`. `runtimeKey` is read when the client needs the host's identity: the send guard, the directory-availability batch, the message-page shells cache and the local-home check. A host built for the registry reads a constant (`() => host.id`); the window client reads `getRuntimeKey`, so its behavior is the one the singleton had.

- **Sends**: `sendMessage`, `sendCommand` and `shellSession` take the caller's captured `runtimeKey` and stop with "Message was not sent because the runtime changed." when it differs from the client's runtime key, before every mutation. Since the facade resolves a method once, when it is called, a send keeps running on the host it started on when the focus moves; it stops only when the key that client reads changes (the window client after a runtime switch).
- **Directory availability**: probes batch per client, and a batch whose runtime key changed before its flush answers `unknown` without a request.
- **Reconnect**: `reconnectToRuntimeBaseUrl()` rebuilds that client's SDK clients over its transport, drops its caches and in-flight reads, and increments its `epoch`. Other clients are untouched. `reconnectAppForTransportSwitch` (`apps/runtimeEndpointReset.ts`) reconnects the focused host's client only.

`opencodeClient` in `lib/opencode/client.ts` is `createFocusFacade(OpencodeService.prototype, () => resolveHost().client)`. `client.ts` and `app-host.ts` import each other; neither uses the other's exports while it loads, so either may load first.
